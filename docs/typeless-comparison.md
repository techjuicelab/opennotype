# Typeless 비교와 군더더기 정리 개선

상태: 2026-09-12 조사. Typeless에 대한 내용은 **공개 페이지에서 읽은 것만** 적었고, 확인 수준을 행마다 표시했다. OpenNoType에 대한 내용은 이 저장소의 코드에서 확인했다. 어느 쪽도 실제 음성으로 측정한 품질 비교가 아니다.

## 확인 수준 표기

| 표기 | 뜻 |
| --- | --- |
| 확인 | Typeless 공식 페이지(제품 사이트·도움말·가격·개인정보 처리방침) 또는 스토어 등록 정보에서 직접 읽음 |
| 추정 | 공식 문서에 없고, 사용자 후기나 부재 증거에서 추론함 |
| 미확인 | 근거를 찾지 못함. 주장으로 쓰지 않음 |

Typeless의 내부 구현(사용 모델, 프로토콜, 스트리밍 여부)은 공개 근거를 찾지 못했다. 이 문서는 그것을 추측하지 않는다.

## 한눈에 보는 차이

요약하면 **Typeless를 그대로 따라갈 대상은 "정리를 제품의 중심으로 놓는 태도"이고, 따라가지 말아야 할 것은 "정리 강도를 사용자가 만질 수 없게 하는 결정"** 이다. 두 언어권 후기에서 공통으로 나오는 불만이 과잉 편집인데, 양쪽 모두 그것을 되돌릴 수단을 제공하지 않는다.

## 우리 쪽 군더더기 제거가 약했던 이유

Typeless와의 차이는 기능 수가 아니라 메커니즘에 있었다. 개선 전 `ProcessingPrompt.swift`에서 필러 정책의 전부는 세 문장이었다.

> Remove nonsemantic fillers, accidental repetitions, abandoned restarts, and superseded parts of clear self-corrections. Retain deliberate emphasis and meaningful repetition.

1. **분류 체계가 없었다.** 네 가지 현상을 이름으로 부르지만 목록도, 순서도, 충돌 시 판정 규칙도 없다. 중재 규칙은 "의도적 강조는 남겨라" 한 문장뿐이고, 그것을 적용할 기준이 없다. 결과적으로 모델이 영어 um/uh 기준으로 학습한 판단을 그대로 쓴다.
2. **한국어의 실제 문제를 건드리지 않았다.** 한국어에서 빈도가 높은 머뭇거림 토큰은 대부분 일반 낱말과 표면형이 같다 — `그`(그것), `이제`(지금), `뭐`(무엇), `막`(방금), `저`(나), `저기`(저곳), `그러니까`(따라서), `어`(응). 표면형이 아니라 기능으로 판단하라는 지시가 없으면 이 구분은 운에 맡겨진다.
3. **완곡 표현이 보이지 않았다.** `좀`, `조금`, `약간`, `그냥`은 요청 강도와 정도를 나른다. `좀 봐줄래`에서 `좀`을 지우면 부탁이 지시가 되는데, 화자는 무엇이 지워졌는지 볼 수 없다.
4. **삭제 허가 옆에 재작성 허가가 붙어 있었다.** "restructure awkward speech into natural sentences"에 경계가 없었다. 화자가 말할 생각이 없던 낱말을 지우는 것과, 말한 낱말을 바꿔 쓰는 것 사이에 선이 없었다. 이것이 경쟁 제품에 제기된 과잉 편집 불만의 메커니즘이기도 하다.
5. **요약 금지 조항이 없었다.** 받아쓰기 경로 어디에도 여러 문장을 합치거나 항목을 빠뜨리는 것을 막는 문장이 없었다.
6. **높임 보존이 다른 블록에 있었다.** `WritingTone.preserve`는 말투 지시에만 있고, 군더더기 제거와 연결되어 있지 않았다.
7. **결과에 영수증이 없다.** `ProviderClient`는 `{"text"}` 한 키만 받으므로 앱은 모델이 무엇을 만들었는지는 알아도 무엇을 지웠는지는 모른다. 감사도 안전한 대체도 불가능하다.
8. **강도가 하드코딩된 하나의 의견이다.** Slack 메시지, 회의 메모, 격식 있는 이메일이 모두 같은 삭제 정책을 받는다.
9. **평가 사례가 문서였지 테스트가 아니었다.** `docs/fixtures/dictation-quality.json`의 사례를 읽는 코드가 없었고, 테스트 안의 별도 사례와 조용히 어긋날 수 있었다. 실제로 검토 중 모순 하나를 찾았다(아래 참고).
10. **군더더기 전용 사례가 사실상 없었다.** 두 집합을 통틀어 disfluency를 건드리는 사례는 둘뿐이었고, 그나마 그렇게 분류되어 있지도 않았다.

## 이번 브랜치에서 한 일 (1단계)

아키텍처·설정·프로바이더 호출을 바꾸지 않고, 프롬프트와 명세와 테스트만 바꿨다.

- `ProcessingPrompt`의 받아쓰기·번역 지시에 **DISFLUENCY POLICY** 블록을 넣었다. 5단계 순서, 한국어 수정 신호 목록, 머뭇거림 토큰 목록, 그리고 표면형이 아니라 기능으로 판단하게 하는 **보존 판정(KEEP TEST)** 으로 구성된다. 애매하면 남기는 쪽으로 편향을 명시했다. 상세는 [받아쓰기 기본 견본](dictation-baseline.md)에 있다.
- 삭제 허가 옆의 재작성 허가에 경계를 두고, 요약·문장 병합·항목 누락·표현 갈아치우기를 명시적으로 금지했다.
- 높임 조항을 말투 설정에 **종속**시켰다. "군더더기 제거는 반말↔존댓말 이동의 이유가 되지 않으며, `writing_profile.tone`만 말투 변경을 허가한다." 무조건 금지로 쓰면 `polite`·`formal` 설정 자체가 무력해진다.
- 끝 무음에서 생기는 영상 마무리 인사 환각을 지우되, 실제로 말한 `감사합니다`는 남기도록 범위를 좁혔다.
- 같은 한국어 문자열이 한 줄에서는 삭제되고 다른 줄에서는 유지되는 **최소 대조쌍 예문 13줄**을 추가했다. 규칙만으로는 전달되지 않는 구분이다.
- 평가 사례를 16건에서 36건으로 늘리고, `disfluency_tokens`(schema_version 2)로 추적 토큰의 출현 **횟수**를 기록했다.
- 사례 파일을 실제로 읽는 테스트(`DisfluencyPolicyTests`)를 추가했다. API 키 없이 돌아가며, 명세 무결성만 검사한다.

선택 문장 수정(`rewrite`) 모드에는 정책을 넣지 않았다. 사용자가 고른 원문에서 군더더기를 말없이 지우면 안 된다.

### 검토 중 찾은 명세 모순

기존 사례 `commit_restart_reconstruction`의 기대 결과가 정도 표현 `조금 더`를 지우고 있었다. 새 보존 판정은 그것을 보호한다. 둘 중 하나는 틀린 것이므로 기대 결과를 `조금 더`를 남기는 쪽으로 고쳤다. 이런 모순이 조용히 생기는 것을 막는 것이 사례 파일을 테스트로 만든 이유다.

### 지시문이 길어진 비용

받아쓰기 지시문이 **4,745~4,901바이트에서 9,103~9,259바이트로** 늘었다(20가지 (형식, 말투) 조합, 소스에서 직접 측정). BYOK 앱이므로 이 증가분은 발화마다 사용자 API 키로 청구된다. 감추지 않고 테스트로 상한(9,600바이트)을 걸어, 앞으로 늘릴 때는 커밋에서 비용을 밝히도록 했다. 프롬프트 캐싱은 아직 적용하지 않았다.

## 아직 하지 않은 것과 이유

| 항목 | 판단 |
| --- | --- |
| 실제 모델로 개선 전후 측정 | **반드시 다음 단계.** 지금까지의 모든 주장은 명세 주장이지 측정이 아니다. 보존 편향을 넣었으므로 삭제가 덜 되는 부작용이 있을 수 있는데, 오프라인 테스트는 원리상 그것을 볼 수 없다 |
| 정리 강도 조절(원문 그대로 / 최소 / 기본 / 적극) | 측정 뒤에. 지금 기본값이 어디에 있는지 모르는 채로 눈금을 만들면 눈금이 거짓말을 한다. `WritingProfile`에 붙이고 `Codable` 마이그레이션이 필요하다 |
| 제거된 부분 표시와 원문 복사 | 데이터는 이미 `HistoryEntry.originalText`에 있다. "실행 취소"가 아니라 "원문 복사"여야 한다. 다른 앱에 이미 넣은 글자를 되돌리는 것은 기존 삽입 확인·클립보드 복원 정책과 충돌한다 |
| 정규식 필러 사전으로 직접 삭제 | 한국어에서 삭제 수단으로는 쓸 수 없다. 조사가 바로 붙어 낱말 경계가 없고(`그거`, `이제는`), 빈도 높은 토큰이 일반 낱말과 표면형이 같다. 후보 **표시** 용도로는 쓸 수 있다 |
| 정리 결과를 다시 검증하는 2차 LLM 호출 | 가장 잦은 경로에서 지연과 비용을 두 배로 만든다. 현재 가진 판정 신호가 너무 거칠다 |
| 의심스러우면 원본 전사로 대체하는 차단 규칙 | 문장 부호도 없고 필러가 그대로인 STT 원문을 남의 앱에 넣는 것이 가벼운 과잉 편집보다 나쁘다 |
| 길이 비율·문장 수로 요약 탐지 | 한국어 STT 결과에는 종결 부호가 아예 없는 경우가 많아 규칙이 동작하지 않고, 느슨하게 만들면 이 저장소의 `final_self_correction` 사례에서 바로 오탐한다 |
| 화면 텍스트 수집으로 앱별 말투 추론 | 우리 정책(허용한 앱, 커서 앞 1,000자, 저장 안 함)에 어긋난다 |
| 스트리밍 부분 출력 | 군더더기 정리 품질을 전혀 올리지 않는다. 참고로 **API가 막고 있는 것은 아니다** — OpenAI 전사 엔드포인트는 `gpt-transcribe` 계열에서 `stream=true`를 지원한다. 이유는 우리 코드 경로가 일괄 처리라는 것과, 의도를 해석하는 정리는 이미 삽입한 글자를 되돌려 지워야 해서 삽입 확인 정책과 충돌한다는 것이다 |
| 단어 단위 타임스탬프·로그확률로 멈춤 감지 | 경로마다 제공 여부가 달라 한 설정에서 품질이 갈린다. OpenAI는 `whisper-1`에서만 `verbose_json` + `timestamp_granularities[]=word`로 단어 타임스탬프를 주고, 기본값인 `gpt-4o-transcribe` 계열은 `json`/`text`만 지원한다. OpenRouter STT는 텍스트만 돌려준다 |
| 정확도·WER·지연 수치 공개 | 측정하기 전까지는 전부 사람이 쓴 명세다. 사례 파일의 `status` 필드도 그렇게 적혀 있다 |
