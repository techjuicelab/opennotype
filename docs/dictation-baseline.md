# 받아쓰기 기본 견본과 앱별 작성 방식

상태: 추가 역인터뷰 합의를 첫 개선판에 반영. 기대 문장은 평가 명세이며 실제 음성이나 모델 평가 통과 결과가 아니다.

경쟁 제품과의 차이와 이 정책을 만든 배경은 [Typeless 비교와 군더더기 정리 개선](typeless-comparison.md)에 있다.

## 음성 인식에 주는 공통 견본

> 일상 대화, 업무 메시지와 메모. 한국어와 영어 등 여러 언어가 섞일 수 있습니다.
> 표기 참고 예문(실제 발화가 아님): 내일 오후 세 시에 만나요. 파일을 Notion에 정리했어요. 여기 weather가 좋네요.

앱에 맞는 상황 설명을 짧게 덧붙인다. 개발 프로필에는 `commit`, `branch`, `merge`, `push`, `pull`, `API`, `GitHub`를 참고 용어로 추가한다. 개인 사전의 원하는 표기를 먼저 선택하고 단어 수·길이를 제한한다. API가 허용하지 않는 제어 문자와 `<`, `>`가 든 용어는 음성 인식 힌트에서 제외한다. 개인 사전 원본은 바꾸지 않는다.

- OpenAI의 지원 모델에는 사전이 비어 있어도 공통 견본을 전달한다. 현재 기본인 `gpt-transcribe`에는 지원하는 `keywords[]`도 전달한다. 다른 모델에 이 필드를 일괄 적용하지 않는다.
- 입력 언어는 자동 감지한다. 번역 목표 언어를 입력 언어로 고정하지 않아 일본어·중국어와 혼합 발화를 계속 받을 수 있다.
- 로컬 Whisper에는 같은 공통 견본과 선택한 용어를 제한된 토큰으로 전달한다.
- OpenRouter 공통 STT 경로에는 동일한 힌트 지원을 가정하지 않는다. 현재는 전사 후 문장 정리 단계에서 사전·프로필을 반영한다.

요청 형식은 [OpenAI 파일 전사 문서](https://developers.openai.com/api/docs/guides/speech-to-text#add-transcription-context), OpenRouter의 적용 한계는 [OpenRouter STT 문서](https://openrouter.ai/docs/guides/overview/multimodal/stt)를 확인했다. 실제 계정 접근 가능성과 품질은 별도 검증 대상이다.

## 기대하는 정리 결과

| 입력 예시 | 기대 결과 |
| --- | --- |
| 일단 커미 처리는 했는데 조금 더 속도나 이런 것들을 좀 개선할 사항들을, 개선할 사항들이 있는지 좀 찾아봐야 될 것 같아요. | 일단 commit 처리는 했는데, 조금 더 속도나 이런 부분에서 개선할 사항이 있는지 좀 찾아봐야 될 것 같아요. |
| 어 음 그 그러면 내일 오후 3시에 보자. | 그러면 내일 오후 3시에 보자. |
| 그 파일 좀 확인해 주세요. | 그 파일 좀 확인해 주세요. |
| 저기 잠깐만요, 어, 저기 이거 맞나요? | 저기, 잠깐만요. 이거 맞나요? |
| 어 그 이제 뭐 그니까 그래서 막 그 결론은 다음 주에 하자. | 그래서 결론은 다음 주에 하자. |
| 커밋하고 파일을 노션에 올렸어요. | commit하고 파일을 Notion에 올렸어요. |
| 오전 7시에 볼까… 아닌가… 오후 3시에 보자. | 오후 3시에 보자. |
| 오전 7시에 볼까… 아닌가… 잘 모르겠어. | 오전 7시에 볼까? 아닌가, 잘 모르겠어. |
| 정말 정말 고마워. 다음에도 꼭 꼭 와 줘. | 정말 정말 고마워. 다음에도 꼭, 꼭 와 줘. |
| 여기 weather 이 좋네 그래도 rain 이 올수도 있겠어. | 여기 weather가 좋네. 그래도 rain이 올 수도 있겠어. |
| 코드에 있는 ‘커미’라는 변수는 이름을 바꾸지 마. | 코드에 있는 ‘커미’라는 변수는 이름을 바꾸지 마. |

`커미`를 무조건 `commit`으로 바꾸는 치환 규칙은 사용하지 않는다. 문맥에서 의도가 명확한 오인식을 복원하되 실제 식별자·이름을 추측하지 않는다.

첫 줄의 `조금 더`는 이전 명세에서 삭제 대상이었으나 이번 개선판에서 보존으로 바꿨다. 아래 **보존 판정(KEEP TEST)** 이 정도 표현을 보호하는데, 같은 파일의 기대 결과가 그것을 지우고 있으면 명세가 스스로 모순되기 때문이다.

## 한국어 군더더기 정리 정책

`ProcessingPrompt`의 받아쓰기·번역 지시에 **DISFLUENCY POLICY** 블록을 넣었다. 이전에는 "nonsemantic fillers를 제거하라"는 한 문장이 전부여서, 모델이 영어 um/uh 기준으로 학습한 판단을 그대로 적용했다. 한국어에서 문제가 되는 이유는 빈도가 높은 머뭇거림 토큰 대부분이 일반 낱말과 표면형이 같기 때문이다.

| 단계 | 내용 |
| --- | --- |
| 1. 자기수정 | 대체할 값이 실제로 말해진 경우에만 앞 값을 버린다. 수정 신호는 `아니`, `아닌가`, `아니고`, `아니라`, `말고`, `아 참`, `아 맞다`, `다시 말하면`. `아니면`과 `또는`은 선택지를 잇는 접속이라 아무것도 지우지 않는다. 결론을 내리지 않았으면 선택지와 망설임을 모두 남긴다. |
| 2. 버려진 재시작 | 화자가 버리고 곧바로 다시 말한 조각만 지운다. 그 조각 안의 완곡 표현도 함께 사라진다. 조각을 대신 완성하지 않는다. |
| 3. 수리성 반복 | 같은 성분을 두 번 말했고 앞이 깨졌거나 조사가 틀렸으면 마지막 완성형만 남긴다. `정말 정말`, `꼭 꼭`처럼 정도를 키우는 반복은 유지한다. |
| 4. 머뭇거림 삭제 | 낱말 사이의 공백을 메우는 자리에서만 지운다: `어`, `어어`, `음`, `으음`, `에`, `아`, `흠`, `그`, `그어`, `저`, `저기`, `이제`, `인제`, `뭐`, `뭐지`, `뭐랄까`, `있잖아`, `그러니까`, `그니까`, `막`, 그리고 uh, um, er, like, you know, I mean. |
| 5. 보존 판정 | 4단계 후보를 지우기 전에 매번 적용한다. |

보존 판정이 이 정책의 핵심이다. 4단계 목록의 낱말은 대부분 일반 낱말이기도 하다 — `그`(그것), `이제`(지금), `뭐`(무엇), `막`(방금·마구), `저`(나), `저기`(저곳·부르는 말), `그러니까`(따라서), `어`(응), `있잖아`(그거 말이야). 표면형이 아니라 **이 발화에서의 기능**으로 판단하고, 지웠을 때 정도·확신·높임·요청 강도·지시 대상·절 사이의 관계·대답이나 반박이 달라지면 남긴다. `좀`, `조금`, `약간`, `그냥`은 요청을 누그러뜨리거나 정도를 조절하므로, 살아남는 문장에 붙은 것은 남긴다(`좀 봐줄래`는 부탁, `봐줄래`는 지시).

**기능이 애매하면 남긴다.** 남긴 군더더기의 비용은 낱말 하나지만, 지워진 의미의 비용은 메시지 전체이고 화자는 무엇이 지워졌는지 볼 수 없다.

정책은 다음도 함께 막는다.

- 군더더기 제거를 이유로 요약하거나, 여러 문장을 합치거나, 항목을 빠뜨리거나, 화자의 표현을 더 매끄러운 말로 갈아치우는 것. 긴 발화는 길게 남는다.
- 군더더기 제거를 이유로 반말↔존댓말을 옮기는 것. 말투 변경은 `writing_profile.tone` 설정만 허가한다.
- 말하지 않은 맺음말 추가. 무관한 발화 뒤에 붙은 `시청해 주셔서 감사합니다`류는 끝 무음에서 생긴 인식 환각이라 지우되, 발화에 어울리는 평범한 `감사합니다`·`수고하세요`는 말한 내용이므로 남긴다.

선택 문장 수정(`rewrite`) 모드에는 이 정책을 넣지 않는다. 사용자가 고른 원문에서 군더더기를 말없이 지우면 안 되기 때문이다.

### 지시문 길이와 비용

정책과 최소 대조쌍 예문을 넣으면서 받아쓰기 지시문이 **4,745~4,901바이트에서 9,103~9,259바이트로** 늘었다((형식, 말투) 20가지 조합 기준, 소스에서 직접 측정). BYOK 앱이므로 이 증가분은 발화마다 사용자의 API 키로 청구된다. `DisfluencyPolicyTests.testInstructionByteBudgetStaysBounded`가 9,600바이트 상한을 검사하므로, 앞으로 상한을 올리려면 커밋에서 비용을 명시해야 한다. 프롬프트 캐싱으로 이 비용을 줄이는 것은 아직 적용하지 않았다.

## 앱별 적용과 설정

설정의 **앱별 작성 방식**에서 형식과 말투를 변경한다. 알려진 설치 앱은 기본값을 보여 주고, 다른 앱은 **앱 추가…**로 지정할 수 있다.

| 형식 | 기본 대상 예 | 정리 범위 |
| --- | --- | --- |
| 일반 | Claude, 브라우저, 미확인 앱 | 자연스러운 문장과 문단 |
| 개발 | Codex, Antigravity, VS Code | 실제 언급한 개발 용어 표기와 요청 구조 |
| 대화 | KakaoTalk, Telegram, Discord | 대화 흐름과 말한 높임말 보존 |
| 메모 | Notes, Notion, Obsidian | 문단 분리, 실제로 나열한 항목의 목록화 |
| 이메일 | Mail | 읽기 좋은 문단; 말하지 않은 인사·수신자·서명 추가 금지 |

모든 기본값은 **말한 말투 유지**다. 명시적으로 설정한 앱에서만 편한 반말·자연스러운 존댓말·격식 있는 존댓말로 바꾼다. 문체를 바꿔도 질문을 통보로 만들거나 불확실한 생각을 약속으로 바꾸면 안 된다.

앱 이름은 프로필을 고르는 데만 쓰고 AI 요청에 보내지 않는다. 브라우저 웹사이트나 메신저 상대별 규칙은 이번 버전에 없다. 주변 문맥은 기존의 별도 앱별 동의를 거쳐야만 전송된다.

녹음 시작 때 선택한 프로필을 끝까지 사용한다. 실패 녹음 재처리에도 그 프로필을 복원한다. 선택 문장 수정은 사용자의 수정 지시를 따르며 자동 문체 설정으로 이를 덮어쓰지 않는다.

## 학습 기준

학습은 STT 원문과 AI 결과의 차이가 아니라, 실제 삽입 결과와 이후 수정의 차이를 비교한다. 따라서 이번 AI의 `커미 → commit` 복원 자체는 개인 사전에 쌓이지 않는다.

현재 학습 관찰은 접근성으로 삽입이 확인된 입력란에서 작동한다. 접근성 확인이 어려운 앱에서는 자동학습을 시작하지 않을 수 있다. 또한 입력란 변경만으로 외부 편집기의 자동 교정과 사람의 수정을 완벽히 구별할 수는 없다. 사전 편집·삭제와 큰 문장 변경의 검토 후보 절차를 유지한다.

## 속도 개선과 측정 범위

- 기록 갱신에서 네 차례 수행하던 전체 저장소 읽기를 하나의 조회로 합쳤다. 암호화 검증·프로세스 간 잠금·만료 처리를 유지한다.
- 화자 필터를 켠 로컬 인식은 필터 결과를 직접 넘긴다. 임시 WAV를 쓰고 다시 읽는 과정을 없앴다.
- 설정의 **입력 문제 확인 → 최근 처리 시간**에서 음성 준비, 음성 인식, 문장 정리, 입력·확인, 기록 갱신 시간을 볼 수 있다.
- 내용 없는 구간별 시간 로그는 다음 명령으로 확인한다.

```sh
/usr/bin/log show --last 10m --style compact --predicate 'subsystem == "app.opennotype.mac" AND category == "pipeline"'
```

`입력·확인`은 붙여넣기 이후 확인 대기를 포함하므로 글이 실제로 보인 시간과 다를 수 있다. 기존 붙여넣기·클립보드 복원·중복 입력 방지 정책은 유지한다. 호출 횟수 감소는 코드상 확인할 수 있지만 실제 사용자 발화의 전체 지연 감소는 아직 측정하지 않았다.

## 동일 음성 평가

[36개 평가 사례](fixtures/dictation-quality.json)는 기준 발화, STT 입력, 기대 결과, 보존 조건과 금지 변화를 구분한다. 의미가 같은 자연스러운 변형은 허용하되 이름·숫자·부정·조건·확신·요청 강도는 별도로 검토한다. 이번 개선판에서 한국어 군더더기 사례 20개를 추가했다.

새 사례는 `disfluency_tokens`(schema_version 2)로 추적 토큰의 **출현 횟수**를 적는다. 포함 여부가 아니라 횟수인 이유는, 같은 표면형이 한 문장 안에서 일부만 삭제되는 경우가 이 문제의 핵심이기 때문이다 — 예를 들어 `그래서 이제 어 이제 시작하려고요`에서 `이제`는 2회 중 1회만 사라진다. 사례 집합은 삭제가 정답인 경우, 보존이 정답인 경우, 일부만 삭제되는 경우를 모두 포함한다. 보존 편향만 검사하는 집합은 아무것도 지우지 않는 모델에 만점을 주기 때문이다.

1. 같은 사용자 녹음을 기존 설정과 개선 설정에 각각 넣어 STT 결과와 최종 결과를 분리해 비교한다.
2. 앱별 프로필, 개인 사전, 주변 문맥 허용 여부를 고정하고 단계별 시간을 기록한다.
3. 무음·잡음에서 견본이 튀어나오지 않는지, 반대로 견본 문장을 실제로 말하면 삭제하지 않는지 확인한다.
4. 현재 모델의 개선을 확인한 뒤 동일 녹음으로 후보 모델의 품질·속도·비용을 비교한다.

실제 평가 음성은 소스 저장소에 넣지 않는다. 평가용으로 보관·전송 범위를 정한 녹음만 사용하며, 앱의 성공 녹음 즉시 삭제 정책을 평가 편의 때문에 자동 변경하지 않는다.
