# 받아쓰기 기본 견본과 앱별 작성 방식

상태: 0.1.9의 기본 프롬프트는 Codex `233fd1f`를 그대로 유지한다. 불필요한 반복을 합치고 고유 정보와 말투를 보존하는 것이 목표이며, 이 문서의 기대 문장은 평가 명세다. 모든 사례에서 모델이 통과했다는 뜻은 아니다.

경쟁 제품과의 차이와 이 정책을 만든 배경은 [Typeless 비교와 군더더기 정리 개선](typeless-comparison.md)에 있다.

## 음성 인식에 주는 공통 견본

> 일상 대화, 업무 메시지와 메모. 한국어와 영어 등 여러 언어가 섞일 수 있습니다.
> 표기 참고 예문(실제 발화가 아님): 내일 오후 세 시에 만나요. 파일을 Notion에 정리했어요. 여기 weather가 좋네요.

앱에 맞는 상황 설명을 짧게 덧붙인다. 개발 프로필에는 `commit`, `branch`, `merge`, `push`, `pull`, `API`, `GitHub`를 참고 용어로 추가한다. 개인 사전의 원하는 표기를 먼저 선택하고 단어 수·길이를 제한한다. API가 허용하지 않는 제어 문자와 `<`, `>`가 든 용어는 음성 인식 힌트에서 제외한다. 개인 사전 원본은 바꾸지 않는다.

- OpenAI의 지원 모델에는 사전이 비어 있어도 공통 견본을 전달한다. 현재 기본인 `gpt-transcribe`에는 지원하는 `keywords[]`도 전달한다. 다른 모델에 이 필드를 일괄 적용하지 않는다.
- 입력 언어는 자동 감지한다. 번역 목표 언어를 입력 언어로 고정하지 않아 일본어·중국어와 혼합 발화를 계속 받을 수 있다.
- 로컬 Whisper에는 같은 공통 견본과 선택한 용어를 제한된 토큰으로 전달한다.
- OpenRouter 공통 STT 경로에는 동일한 힌트 지원을 가정하지 않는다. 현재는 전사 후 문장 정리 단계에서 사전·프로필을 반영한다.

요청 형식은 [OpenAI 파일 전사 문서](https://developers.openai.com/api/docs/guides/speech-to-text#add-transcription-context), OpenRouter의 적용 한계는 [OpenRouter STT 문서](https://openrouter.ai/docs/guides/overview/multimodal/stt)를 확인했다. 실제 계정 접근 가능성과 품질은 별도 검증 대상이다.

`커미`를 무조건 `commit`으로 바꾸는 치환 규칙은 사용하지 않는다. 문맥에서 의도가 명확한 오인식을 복원하되 실제 식별자·이름을 추측하지 않는다.

첫 줄의 `조금 더`는 추가 개선의 정도를 나타내므로 남긴다. 같은 부탁을 다시 시작하더라도 앞 조각의 `좀`이나 `조금 더`가 마지막 요청에도 적용되면 이어받는다. 남은 문장의 어순은 자연스럽게 바꿀 수 있지만, 그 과정에서 부탁의 강도나 정도를 바꾸면 안 된다.

## 한국어 군더더기 정리 평가 기준

`ProcessingPrompt`는 받아쓰기·번역 지시에 `DictationCleanupInstructions`의 공유 정리 계약을 조합한다. 두 소스는 Codex `233fd1f`와 같다. 아래 상세 기준과 대조 사례는 Claude 조사에서 보완한 평가 명세이며, 후보의 **DISFLUENCY POLICY**·**KEEP TEST** 블록을 기본 코드에 추가한 것은 아니다. 예를 들어 `그`는 빈 머뭇거림일 수도, 특정 문서를 가리키는 지시어일 수도 있다.

| 단계 | 내용 |
| --- | --- |
| 1. 자기수정 | 대체할 값과 정정 의도가 모두 명확할 때 해당 항목만 바꾼다. 수정 신호 후보는 `아니`, `아닌가`, `아니고`, `아니라`, `말고`, `아 참`, `아 맞다`, `다시 말하면`이지만 단어만으로 정정을 단정하지 않는다. 수정하지 않은 행동·상대·장소·조건은 남긴다. 값만 고쳐도 질문이 결정으로 바뀌지는 않는다. `아니면`과 `또는`은 선택지를 잇고, 미결정 상태나 별도로 추가한 일정은 보존한다. |
| 2. 버려진 재시작 | 화자가 다시 시작한 불완전한 조각을 완성된 문장에 합친다. 동일한 부탁에 적용되는 `좀`, `조금 더`와 조건·정도는 앞 조각에만 있어도 이어받는다. 화자가 명확히 철회한 내용만 버리고, 근거 없이 조각을 완성하거나 새 내용을 만들지 않는다. |
| 3. 중복 정리 | 같은 사실을 불필요하게 다시 말하면 하나로 합치고, 다시 말하며 추가한 고유 정보는 모두 남긴다. 마지막 완성형만 고르는 방식으로 앞의 조건이나 대상을 잃지 않는다. `정말 정말`, `꼭 꼭` 같은 강조, 실제 반복 사건·횟수·절차, 인용·코드 속 반복은 유지한다. |
| 4. 머뭇거림 삭제 | 낱말 사이의 공백을 메우는 자리에서만 지운다: `어`, `어어`, `음`, `으음`, `에`, `아`, `흠`, `그`, `그어`, `저`, `저기`, `이제`, `인제`, `뭐`, `뭐지`, `뭐랄까`, `있잖아`, `그러니까`, `그니까`, `막`, 그리고 uh, um, er, like, you know, I mean. |
| 5. 보존 판정 | 4단계 후보를 지우기 전에 매번 적용한다. |

보존 판정이 이 명세의 핵심이다. 4단계 목록의 낱말은 대부분 일반 낱말이기도 하다 — `그`(그것), `이제`(지금), `뭐`(무엇), `막`(방금·마구), `저`(나), `저기`(저곳·부르는 말), `그러니까`(따라서), `어`(응), `있잖아`(그거 말이야). 표면형이 아니라 **이 발화에서의 기능**으로 판단하고, 지웠을 때 정도·확신·높임·요청 강도·지시 대상·절 사이의 관계·대답이나 반박이 달라지면 남긴다. `좀`, `조금`, `약간`, `그냥`이 요청을 누그러뜨리거나 정도를 조절하면 남긴다. 앞 재시작 조각에 있었다는 위치만으로 삭제하지 않는다. `봐줄래`도 질문형 부탁이지만, `좀 봐줄래`의 완화된 태도를 자연스러운 정리라는 이유로 잃어서는 안 된다.

**기능이 애매하면 남긴다.** 기본 정리는 의미 없는 반복을 줄이지만, 애매한 부분에서 정보를 버리는 쪽으로 추측하지 않는다. 기록에 남긴 STT 원문과 정리 결과의 비교·복사 및 선택 재처리는 자동 입력 뒤 검토를 돕는 수단이며, 첫 결과의 내용 유실을 허용하는 근거가 아니다.

평가에서는 다음 변화도 실패로 본다.

- 군더더기 제거를 이유로 요약하면서 고유 정보·조건·부정·불확실성·요청 강도를 빠뜨리는 것. 여러 문장의 중복 병합과 자연스러운 어순 조정은 허용하지만 모든 고유 정보와 관계를 남겨야 한다. 글자 수나 문장 수 자체가 의미 보존 점수는 아니다.
- 군더더기 제거를 이유로 반말↔존댓말을 옮기는 것. 말투 변경은 `writing_profile.tone` 설정만 허가한다.
- 말하지 않은 맺음말 추가 또는 원문 맺음말의 근거 없는 삭제. 텍스트 후처리는 원본 음성이나 무음 판정 근거를 받지 않는다. `시청해 주셔서 감사합니다`가 문맥상 어색하거나 흔한 인식 환각 패턴이어도 그것만으로 발화 여부를 판단하지 않는다. 원문에 있는 인사는 보존하고, 실제 인식 환각 여부는 음성을 포함한 별도 평가에서 확인한다.

선택 문장 수정(`rewrite`) 모드에는 받아쓰기의 공유 정리 계약을 넣지 않는다. 사용자가 고른 원문에서 군더더기를 말없이 지우면 안 되기 때문이다.

### 지시문 길이와 비용

기본 정리는 별도의 AI 검수 요청을 덧붙이지 않고 한 번의 문장 정리 요청 안에서 수행한다. STT 요청과 사용자가 직접 선택한 기록 재처리는 각각 별도 작업이다. `DisfluencyPolicyTests.testInstructionByteBudgetStaysBounded`는 받아쓰기 지시문의 UTF-8 크기 상한을 검사해 프롬프트가 무제한으로 커지는 것을 막는다. 이 바이트 수는 청구 토큰 수가 아니다. 실제 사용량과 비용은 모델의 토큰화, 응답 토큰, 공급자 단가와 캐시 사용 여부로 확인해야 하며, 크기 상한을 늘릴 때에는 측정 근거를 남긴다.

최종 채택한 Codex 프롬프트는 전체 20개 형식·말투 조합에서 **최대 9,112 UTF-8 바이트**이며 테스트 상한 10,400바이트 이내다. 통합 후보의 측정값을 채택 버전의 수치로 사용하지 않는다. 같은 합성 사례 9개에서 정리 통과는 Codex 7개, 개정 후보 6개였고 의미 보존은 둘 다 9개였다. 기본값 변경을 뒷받침할 개선을 확인하지 못해 Codex 소스를 유지했다. 자세한 판정·비용·지연과 미채택 후보 증거는 [실제 모델 비교 기록](reviews/2026-09-12/faithful-cleanup-live-comparison.md)을 따른다.

## 앱별 적용과 설정

설정의 **앱별 작성 방식**에서 형식과 말투를 변경한다. 알려진 설치 앱은 기본값을 보여 주고, 다른 앱은 **앱 추가…**로 지정할 수 있다.

| 형식 | 기본 대상 예 | 정리 범위 |
| --- | --- | --- |
| 일반 | Claude, 브라우저, 미확인 앱 | 자연스러운 문장과 문단 |
| 개발 | Codex, Antigravity, VS Code | 실제 언급한 개발 용어 표기와 요청 구조 |
| 대화 | KakaoTalk, Telegram, Discord | 대화 흐름과 말한 높임말 보존 |
| 메모 | Notes, Notion, Obsidian | 문단 분리, 실제로 나열한 항목의 목록화 |
| 이메일 | Mail | 읽기 좋은 문단; 말하지 않은 인사·수신자·서명 추가 금지 |

모든 기본값은 **말한 말투 유지**다. 명시적으로 설정한 앱에서만 편한 반말·자연스러운 존댓말·격식 있는 존댓말로 바꾼다. 문체를 바꿔도 질문을 통보로 만들거나 불확실한 생각을 약속으로 바꾸면 안 된다.

앱 이름은 프로필을 고르는 데만 쓰고 AI 요청에 보내지 않는다. 브라우저 웹사이트나 메신저 상대별 규칙은 이번 버전에 없다. 주변 문맥은 기존의 별도 앱별 동의를 거쳐야만 전송된다.

녹음 시작 때 선택한 프로필을 끝까지 사용한다. 실패 녹음 재처리에도 그 프로필을 복원한다. 선택 문장 수정은 사용자의 수정 지시를 따르며 자동 문체 설정으로 이를 덮어쓰지 않는다.

## 학습 기준

학습은 STT 원문과 AI 결과의 차이가 아니라, 실제 삽입 결과와 이후 수정의 차이를 비교한다. 따라서 이번 AI의 `커미 → commit` 복원 자체는 개인 사전에 쌓이지 않는다.

현재 학습 관찰은 접근성으로 삽입이 확인된 입력란에서 작동한다. 접근성 확인이 어려운 앱에서는 자동학습을 시작하지 않을 수 있다. 또한 입력란 변경만으로 외부 편집기의 자동 교정과 사람의 수정을 완벽히 구별할 수는 없다. 사전 편집·삭제와 큰 문장 변경의 검토 후보 절차를 유지한다.

## 속도 개선과 측정 범위

- 기록 갱신에서 네 차례 수행하던 전체 저장소 읽기를 하나의 조회로 합쳤다. 암호화 검증·프로세스 간 잠금·만료 처리를 유지한다.
- 화자 필터를 켠 로컬 인식은 필터 결과를 직접 넘긴다. 임시 WAV를 쓰고 다시 읽는 과정을 없앴다.
- 설정의 **입력 문제 확인 → 최근 처리 시간**에서 음성 준비, 음성 인식, 문장 정리, 입력·확인, 기록 갱신 시간을 볼 수 있다.
- 내용 없는 구간별 시간 로그는 다음 명령으로 확인한다.

```sh
/usr/bin/log show --last 10m --style compact --predicate 'subsystem == "app.opennotype.mac" AND category == "pipeline"'
```

`입력·확인`은 붙여넣기 이후 확인 대기를 포함하므로 글이 실제로 보인 시간과 다를 수 있다. 기존 붙여넣기·클립보드 복원·중복 입력 방지 정책은 유지한다. 호출 횟수 감소는 코드상 확인할 수 있지만 실제 사용자 발화의 전체 지연 감소는 아직 측정하지 않았다.

## 동일 음성 평가

[38개 평가 사례](fixtures/dictation-quality.json)는 기준 발화, STT 입력, 기대 결과, 보존 조건과 금지 변화를 구분한다. 의미가 같은 자연스러운 변형은 허용하되 이름·숫자·부정·조건·확신·요청 강도는 별도로 검토한다. 기존 16개와 한국어 군더더기 사례 20개에, 음성 근거 없는 단독 맺음말 보존과 재시작 앞의 정도 표현 승계 2개를 더했다. `case_count`는 실제 사례 수와 일치해야 한다.

새 사례는 `disfluency_tokens`(schema_version 2)로 추적 토큰의 **출현 횟수**를 적는다. 포함 여부가 아니라 횟수인 이유는, 같은 표면형이 한 문장 안에서 일부만 삭제되는 경우가 이 문제의 핵심이기 때문이다 — 예를 들어 `그래서 이제 어 이제 시작하려고요`에서 `이제`는 2회 중 1회만 사라진다. 사례 집합은 삭제가 정답인 경우, 보존이 정답인 경우, 일부만 삭제되는 경우를 모두 포함한다. 보존 편향만 검사하는 집합은 아무것도 지우지 않는 모델에 만점을 주기 때문이다. 이 횟수는 사람이 작성한 입력·기대 예시 사이의 무결성 메타데이터이며, 의미가 같은 실제 출력의 표현을 고정하는 점수가 아니다.

`DisfluencyPolicyTests`는 명세 필드, 토큰 횟수, 요청 데이터 격리와 프롬프트 조합을 검사한다. 녹음이나 모델을 실행하지 않으므로 이 검사 통과만으로 중복 제거 또는 의미 보존에 성공했다고 판단하지 않는다. 별도의 [32개 충실한 정리 사례](fixtures/faithful-cleanup.json)와 실모델 출력에서는 의미 보존과 정리 품질을 독립적으로 판정하고, 전송·형식 오류는 내용 평가와 분리한다.

1. 같은 사용자 녹음을 기존 설정과 개선 설정에 각각 넣어 STT 결과와 최종 결과를 분리해 비교한다.
2. 앱별 프로필, 개인 사전, 주변 문맥 허용 여부를 고정하고 단계별 시간을 기록한다.
3. 무음·잡음에서 견본이 튀어나오지 않는지, 반대로 견본 문장을 실제로 말하면 삭제하지 않는지 확인한다.
4. 현재 모델의 개선을 확인한 뒤 동일 녹음으로 후보 모델의 품질·속도·비용을 비교한다.

실제 평가 음성은 소스 저장소에 넣지 않는다. 평가용으로 보관·전송 범위를 정한 녹음만 사용하며, 앱의 성공 녹음 즉시 삭제 정책을 평가 편의 때문에 자동 변경하지 않는다.
