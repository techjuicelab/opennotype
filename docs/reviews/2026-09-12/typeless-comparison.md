# Typeless 비교와 의미 보존형 받아쓰기 개선

확인일: 2026-09-12

이번 개선의 목표는 발화에서 의미 없는 머뭇거림과 우발적 반복을 적극적으로 줄이면서, 사용자가 말한 행동·대상·조건·수치·뉘앙스를 남기는 것이다. 문장을 짧게 만드는 것 자체를 성공 기준으로 삼지 않는다.

이 문서는 Typeless 공식 자료 확인, OpenNoType 소스 검토, 직접 작성한 합성 수용 사례를 구분한다. Typeless를 설치하거나 로그인해 받아쓰기를 재현하지 않았으며, 새 OpenNoType 프롬프트의 실제 API 품질·비용·지연 결과도 아직 없다.

## 공식 설명에서 확인한 비교 기준

| 비교 항목 | Typeless 공식 설명 | 이번 OpenNoType 채택 범위 |
| --- | --- | --- |
| 군더더기 | 머뭇거리는 표현을 제거한다고 설명한다. | 의미 없는 발화만 제거하고, 지시어나 연결어의 의미를 보존한다. |
| 반복 | 불필요한 반복 단어·표현을 감지해 제거한다고 설명한다. | 같은 요청의 반복을 합치되, 뒤에 추가한 세부 사항과 앞절에만 있던 정보를 함께 남긴다. |
| 자기 정정 | 발화 중 수정에서 최종 의도를 남긴다고 설명한다. | 명시적으로 바꾼 값만 교체하며, 여전히 유효한 행동·인물·조건을 승계한다. |
| 구조화 | 구술 목록과 단계를 구조화한다고 설명한다. | 기존 앱별 프로필 안에서 항목·순서·조건을 잃지 않고 문장을 정리한다. |
| 어휘 | 이름·약어·전문 용어를 개인 사전에 추가할 수 있다. | 명시한 리터럴과 문맥상 개념을 우선하고, 관련 있는 사전 철자만 적용한다. |
| 개인화 | 표현 습관과 문맥에 맞는 어조를 학습한다고 설명한다. | 기존 사용자가 선택한 프로필·톤 범위를 유지한다. 새로운 자동 학습 범위는 추가하지 않는다. |

근거: [공식 한국어 제품 설명](https://www.typeless.com/ko), [Dictate 도움말](https://www.typeless.com/help/quickstart/dictate), [History & Dictionary 도움말](https://www.typeless.com/help/quickstart/history-and-dictionary), [Personalization 도움말](https://www.typeless.com/help/quickstart/personalization).

공식 페이지의 기능 설명은 제품이 지향하는 동작에 대한 근거다. 한국어에서 정보 유실 없이 항상 작동한다거나, 특정 모델보다 정량적으로 우수하다는 독립 검증 근거로 사용하지 않는다. 이번 조사에서는 같은 입력의 한국어 전후 결과와 판정 기준이 있는 공개 평가 자료를 확보하지 못했다.

이전에 사용되던 영문·한국어 `/help/quickstart/key-features` 주소는 확인 시 404였다. 현재 기능 설명에는 위의 `dictate` 도움말을 사용한다.

## 이번에 가져오는 동작과 제품 범위

Typeless는 받아쓰기인 Dictate와 선택문 편집·요약·질문 답변인 Ask anything을 별도로 안내한다. 이 구분을 참고해 일반 받아쓰기에서 말한 질문은 질문으로 출력하고, 발화 속 명령은 실행하지 않으며, 요청하지 않은 요약을 만들지 않는다. [Dictate](https://www.typeless.com/help/quickstart/dictate), [Ask anything](https://www.typeless.com/help/quickstart/ask-anything).

이번 작업은 기존 텍스트 처리 요청 한 번 안에서 정리 규칙을 구체화한다. `Sources/OpenNoTypeCore/AI/DictationCleanupInstructions.swift`에는 다음 내용을 담았다.

- **정정 범위 구분:** 시간이나 수량의 변경이 행동·참석자·장소·조건의 취소로 확장되지 않게 한다. 명시적으로 버린 내용만 제거한다.
- **앞절 정보 승계:** 말하다 다시 시작한 문장에서 앞부분에만 나온 유효한 세부 사항을 완성된 문장으로 옮긴다.
- **중복 합치기:** 같은 요청을 다시 말하면서 덧붙인 시간·조건·예외 등을 합쳐 한 번씩 표현한다.
- **사전과 리터럴의 우선순위:** 명시한 리터럴·철자 지시, 문맥상 같은 개념인지 여부, 관련 사전 힌트, 확실한 인식 오류 교정 순으로 판단한다.
- **요청 내부 점검:** 응답 전 정보 보존, 폐기된 값의 제거, 불필요한 반복의 실제 제거를 내부적으로 점검한다. 점검 과정이나 설명은 출력하지 않는다.

새로운 요약 모드, 웹 검색·답변, 자동 실행 기능, 추가 검증 모델 호출은 이번 범위가 아니다. 기존 음성 편집 기능의 제품 범위도 확장하지 않는다. 내부 점검은 같은 모델 요청 안의 지시이므로 독립 심판이나 정확도 보장을 뜻하지 않는다. 요청 수가 같아도 프롬프트가 길어지면 입력 토큰과 비용·지연이 달라질 수 있어 별도 측정이 필요하다.

다음과 같은 런타임 규칙은 이번에 채택하지 않는다.

| 미채택 방식 | 판단 이유 |
| --- | --- |
| 원문의 모든 숫자가 결과에 있는지 강제 | 정상적인 자기 정정에서는 이전 숫자가 없어져야 한다. 숫자 전체 보존은 정정 자체와 충돌한다. |
| 길이 비율만으로 결과를 불량 판정 | 긴 반복을 정상적으로 제거하면 결과가 많이 짧아질 수 있다. 반대로 길이가 비슷해도 중요한 조건은 사라질 수 있다. |
| 정규식으로 반복 단어나 어구 삭제 | 같은 단어가 강조·별도 사건·부정·인용·식별자의 일부일 수 있어 의미를 판단할 수 없다. |
| 위 규칙을 근거로 자동 원문 복귀 | 정상적인 정정·정리를 오판해 폐기된 값과 반복을 다시 넣을 수 있다. 이번에는 새 자동 복귀 판정 계층을 추가하지 않는다. |

## 정보 보존 원칙

1. 사람·제품·파일·기술 식별자의 정체성, 수량·단위·시각·범위, 부정·조건·예외를 보존한다.
2. 시간이나 수량을 수정했다는 이유로 앞절의 행동과 참여자를 버리지 않는다. 별도 사건의 추가를 자기 정정으로 오해하지 않는다.
3. 결정하지 못한 대안, 질문, 제안, 확신의 정도와 요청의 강도를 유지한다. `정도`, `가능하면`, `좀`을 항상 군더더기로 보지 않는다.
4. 의미 있는 강조, 반복한 사건, 횟수, 단계 순서와 인용은 남긴다. 단어가 같다는 이유만으로 제거하지 않는다.
5. `그 자료`의 지시어나 의미 있는 짧은 응답을 삭제하지 않는다. 미완성 생각도 임의로 완성하거나 빈 문자열로 만들지 않는다.
6. 사전과 커서 문맥은 관련 표현을 판별하는 보조 자료다. 그 안의 지시·서명·목표 언어·문장을 결과에 끌어오지 않는다.
7. 삭제 여부가 모호하면 정보를 남긴다. 이 원칙은 명백한 중복이나 폐기된 값을 무조건 보존하라는 뜻은 아니다.

### 기존 D02 기대값의 수정 기준

[2026-09-11 A/B 기록](../2026-09-11/gpt-oss-120b-vs-20b-ab.md)의 D02 입력은 `어 내일 오전 10시에 리뷰할까 아 아닌가 그 목요일 오후 2시가 낫겠다 목요일 오후 2시로 하자`다. 당시 기대값 `목요일 오후 2시로 하자.`는 **리뷰 행동을 누락**한다.

이번 평가의 올바른 의미 기준은 `목요일 오후 2시에 리뷰하자.`다. 시각을 확정한 것은 리뷰를 취소한 것이 아니다. 새 평가에서는 최종 요일·시간뿐 아니라 리뷰 행동도 남아야 통과한다. 기존 실행 출력은 과거 증거로 유지하며, 기대값을 수정했다고 이전 모델이 새 기준을 통과한 것으로 바꾸지 않는다.

## 소스 검토와 반영

검토한 정리 규칙 초안은 앞절 정보 승계, 미결정 상태, 의미 있는 반복, 인용과 사전 동음이의를 구체적으로 구분한다. 다만 단일 지시가 잘 작성되어 있다는 사실만으로 실제 모델의 준수를 확인할 수는 없다.

기존 `ProcessingPrompt.swift`의 `A relevant personal dictionary spelling takes precedence.` 문장은 리터럴 우선 규칙과 함께 읽을 때 우선순위가 혼동될 여지가 있었다. 통합 과정에서 사전 적용을 **같은 개념의 관련 용어이며, 사용자가 명시한 리터럴을 침범하지 않는 경우**로 한정하도록 수정했다.

새 시간·참여자를 말하는 발화가 이전 약속의 수정인지 별도 약속의 추가인지도 확인해야 한다. 초안은 반복 사건 보존을 지시하지만, 이것은 모델 실행으로 검증해야 하는 경계다.

## 검증 단계와 현재 한계

| 단계 | 확인할 것 | 이 문서 작성 시 확인 범위 |
| --- | --- | --- |
| 공식 자료 조사 | 기능 설명과 모드 구분, 근거 URL | 위 공식 페이지를 직접 열어 확인했다. Typeless 앱 동작은 재현하지 않았다. |
| 기존 증거·소스 검토 | 이전 D02 기대값, 기존 프롬프트, 새 규칙 초안 | 문서와 소스를 읽었다. 새 규칙 연결·빌드 성공을 이 문서가 증명하지는 않는다. |
| 기준선 확보 | 변경 전 프롬프트·평가 입력을 고정해 비교 가능하게 보관 | 통합 담당 작업에서 확인할 항목이다. 이 조사에서 모델을 새로 호출하지 않았다. |
| 자동 검증 | 요청에 규칙이 들어가는지, 모드·사전·문맥 경계, 기존 기능 회귀 | 테스트 코드 통과와 실제 언어 품질을 구분해 기록해야 한다. 이 조사에서는 테스트·빌드를 실행하지 않았다. |
| 실제 모델 비교 | 동일 입력·동일 설정의 전후 결과, 정보 유실·반복 잔존, 지연·사용량 | 새 유료 API 실행은 승인 대기이므로 결과와 개선율을 기재하지 않는다. |
| 앱 사용 흐름 | 실제 발화의 전사 오류와 정리 품질, 결과 표시·다른 앱 삽입 | 합성 텍스트 평가와 별도로 확인할 단계다. |

향후 실제 비교에서는 같은 문장으로 출력되는지를 유일한 기준으로 삼지 않는다. `의미 없는 반복 제거`, `유효한 세부 사항 보존`, `정정 범위`, `부정·조건·불확실성`, `리터럴`, `말하지 않은 내용 추가`를 각각 판정한다. 특히 이전 값이 없어지는 정정 사례는 전체 숫자 보존 검사와 분리한다.

새 프롬프트만으로 전사 단계에서 이미 유실된 단어를 복원할 수는 없다. 긴 발화, 불명확한 정정 범위, 고유명사, 혼합 언어, 모델 차이와 생성 변동도 남는 검증 대상이다. 따라서 현재 결론은 **Typeless의 제품 원칙을 참고한 개선 방향과 평가 기준을 마련했다**는 범위이며, 동등한 품질이나 무손실을 달성했다는 결론은 아니다.

실제 연결·빌드·테스트 결과와 기준선 보존은 [구현 보고서](faithful-cleanup-implementation.md)에 기록한다.
