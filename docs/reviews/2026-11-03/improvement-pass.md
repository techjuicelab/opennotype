# 2026-11-03 개선 작업: 입력 지연·녹음 종료 경계·문서 정리

- 기준: main `971e97858f5c5792f82833e68acb7114bb256073` (0.2.12 (48)). 버전·태그·공개 배포는 바꾸지 않았다.
- 범위: 소스·테스트·문서 변경. 설치된 앱 교체, 실제 마이크·API·외부 앱 입력은 하지 않았다.

## 1. 사용량 저장이 자동 입력을 늦추던 문제

### 원인

AI 요청 하나가 끝날 때마다 `ProviderClient`는 사용량 콜백이 끝나기를 기다렸다. 앱의 콜백은 그 안에서 `SecureStore.appendUsage`(암호화 저장소 전체 다시 쓰기)와 `refreshData()`(전체 다시 읽기)를 모두 기다렸다. 저장소는 기록·사용량(최대 10,000건)을 한 파일에 담으므로, 이 시간이 쌓인 데이터 양에 비례해 음성 인식 → 문장 처리 → 자동 입력 사이에 그대로 더해졌다.

`SecureStore`는 읽기만 하는 작업에서도 변경 감지를 위해 저장소 전체를 두 번 JSON으로 다시 인코딩했고, 쓰기에서는 같은 내용을 한 번 더 인코딩했다.

### 변경

- `SecureStore`: 읽기 전용 접근(`snapshot`, `history`, `usageRecords`, `dictionary`, `failures`, `failureAudio`, `speakerProfile`, `learningCandidates`, `jevRepairLessons`)은 같은 잠금·키 확인·만료/이전 처리 후 재인코딩 없이 읽는다. 쓰기는 비교에 쓴 인코딩을 그대로 암호화한다. 기록 직후 다시 읽어 검증하는 단계는 유지했다.
- `AppModel`: 사용량은 요청 순서대로 하나의 작성기가 저장한다. 녹음 처리 파이프라인(받아쓰기·번역·선택 문장 수정·프롬프트, 복구 녹음 다시 처리)은 기록을 확정만 하고 바로 다음 단계로 진행하며, 대기 상태로 돌아가기 전에 저장 완료를 기다린다. 다른 검토·재처리 기능은 이전처럼 저장과 화면 갱신을 마친 뒤 진행한다. 여러 기록은 저장 후 한 번만 다시 읽는다.
- 취소·수집 끄기·초기화의 기존 계약은 유지했다. 확정된 기록은 끝까지 저장하고, 초기화 이전에 시작한 요청은 저장소의 초기화 경계가 걸러낸다. 저장 실패 경고도 같다.

### 측정

Apple M2 Max, macOS 27.2, release 빌드. 합성 기록·사용량으로 만든 암호화 저장소와 즉시 응답하는 로컬 HTTP 대역을 사용했다. 실제 네트워크·제공자 지연은 포함하지 않는다.

저장소 연산 (사용량 10,000건 + 기록 3,000개, 평문 약 9 MB):

| 연산 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| `snapshot` (화면 갱신 읽기) | 305 ms | 102 ms |
| `appendUsage` (사용량 1건 쓰기) | 520 ms | 420 ms |

복구 녹음 다시 처리 전체 흐름(음성 인식 1회 + 문장 처리 1회):

| 저장된 데이터 | 인식 응답 → 문장 요청 시작 (전 / 후) | 문장 응답 → 결과 준비 (전 / 후) | 전체 작업 (전 / 후) |
| --- | ---: | ---: | ---: |
| 사용량 200 · 기록 60 | 20 / 1 ms | 20 / 2 ms | 86 / 59 ms |
| 사용량 3,000 · 기록 900 | 250 / 1 ms | 251 / 2 ms | 1,057 / 692 ms |
| 사용량 10,000 · 기록 3,000 | 821 / 1 ms | 833 / 1 ms | 3,494 / 2,235 ms |

결과 준비 시점이 자동 입력 직전이다. 결과 준비 후 대기 상태까지 남은 시간은 기록·사용량 저장과 화면 갱신이며, 큰 저장소에서는 여전히 다음 녹음 시작을 늦출 수 있다. 저장소를 영역별 파일로 나누는 것이 다음 단계 후보다.

## 2. 녹음 종료가 멈춘 저장 작업을 무기한 기다리던 문제

[2026-10-15 후속 보고서](../2026-10-15/handy-audit-followup.md)의 남은 개선 1번에 해당한다.

- `AudioCapture.snapshot`은 별도 잠금으로 이미 저장된 PCM만 복사한다. 실시간 미리보기가 변환·저장 큐를 기다리지 않는다.
- `AudioCapture.finish`는 큐를 최대 5초 기다린다. 그 안에 비워지지 않으면 녹음을 포기(`captureDeliveryStalled`)하고, 늦게 끝난 변환·쓰기·이벤트는 더 반영하지 않는다.
- `AudioRecorder`는 포기한 녹음의 WAV를 읽지 않고 삭제하며 `stop()`이 파일을 반환하지 않는다. 앱은 기존 ‘녹음 파일 없음’ 경로로 오류를 표시하고, 불완전한 파일을 전사·자동 입력·복구 저장에 쓰지 않는다.
- 남은 한계: 멈춘 작업 자체를 중단하거나 그 녹음을 복구하지는 못한다. 최대 5초 동안은 메인 스레드가 기다린다. 실제 장치에서 저장 작업이 멈추는 상황은 재현하지 않았다.

## 3. 후속: 복호화한 저장소 재사용

1번 이후에도 큰 저장소에서는 입력 뒤 대기 상태까지 1초 이상 걸렸다. 매 접근마다 저장소 전체를 다시 읽고 복호화·디코딩했기 때문이다.

- `SecureStore`는 마지막으로 복호화·검증한 저장소를 파일 식별 정보(inode·크기·수정/상태 변경 시각)와 함께 보관하고, 식별 정보가 같을 때만 재사용한다. 모든 커밋은 새 파일을 rename하므로 다른 프로세스의 쓰기는 inode를 바꾸고, 제자리 수정은 상태 변경 시각을 바꾼다. 캐시에는 커밋 직후 검증 디코딩 결과만 넣는다.
- 사용량·기록 추가는 변경 여부를 직접 알려 변경 감지용 사전 인코딩을 생략한다. 이미 저장된 같은 사용량 기록은 다시 쓰지 않는다.
- 저장 형식은 바꾸지 않았으므로 이전 버전 앱과 Prompt Test 앱도 같은 파일을 읽는다.

| 사용량 10,000건 · 기록 3,000개 | 1번 적용 후 | 캐시 적용 후 |
| --- | ---: | ---: |
| `snapshot` | 102 ms | 1 ms |
| `appendUsage` | 420 ms | 214 ms |
| 복구 녹음 다시 처리 전체 | 2,235 ms | 1,176 ms |
| 같은 흐름, 사용량 3,000 · 기록 900 | 692 ms | 361 ms |

다른 인스턴스의 커밋 위에 쓰기, 파일 교체·삭제 뒤 재사용 금지, 같은 기록 반복 시험을 추가했다. 식별 확인을 빼면 기존 다중 인스턴스 시험을 포함해 49개가 실패하는 것도 확인했다. 남은 쓰기 비용은 한 번의 인코딩과 커밋 직후 검증 디코딩이다. 이 단계 적용 후 같은 하네스에서 Core 662개(opt-in 2개 제외)·Platform 614개가 실패 없이 통과했다.
