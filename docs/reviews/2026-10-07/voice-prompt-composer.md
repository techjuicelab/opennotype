# 음성 작업 프롬프트 개발 기록

2026-10-07, `main`의 `f8a2adf`에서 새 브랜치 `codex/voice-prompt-composer`를 만들었다. 기존 받아쓰기·번역과 별도로, 불규칙한 발화를 코드나 직접 설계가 없는 간결한 요구사항 프롬프트로 변환한다. 공개 릴리스·설치 앱 교체는 이 작업에 포함하지 않았다.

## 분담과 구현

| 담당 | 범위 |
| --- | --- |
| 에이전트 1 | 프롬프트 생성·최종 다듬기 계약, 설정 분리, 코드·설계 제외 지침과 테스트 |
| 에이전트 2 | 공식 API 확인, Jev 4축 검토·엄격한 파서·목적별 기록 검토 |
| 에이전트 3 | 홈·메뉴·결과 복사 화면, 네 번째 단축키와 기존 설정 이주 |
| 에이전트 4 | 독립 통합 감사, runner 호출 순서·실패·취소·크기 한도 회귀 테스트 |
| 통합 담당 | 음성·복구·기록 다시 처리 연결, 수명/취소, 사용량, 문서와 빌드 검증 |

실행 슬롯 제한에 따라 1~3 담당을 먼저 시작하고 UI 완료 뒤 네 번째 담당을 투입했다. 새 채팅 네 개를 만든 것이 아니라 현재 작업의 하위 에이전트 네 개를 사용했다.

초안과 최종 결과는 각각 독립 Jev 검토를 거친다. 최종 통과는 네 축 모두 pass probability ≥0.8 및 confidence ≥0.6일 때다. 이 임계값은 미보정 제품 정책이며 정확도 백분율이 아니다. 실패·불확실·잘못된 응답은 완성 결과로 제공하지 않는다. 첫 검토의 고정 문제 유형만 한 번의 최종 다듬기에 전달한다. 상대 AI가 쓸 코드나 설계·도구 흐름을 생성하지 않는다.

최종 결과는 복사 전용이며 외부 앱 입력·AI 제출을 실행하지 않는다. `InputMode.prompt`는 기존 언어/표현·번역·개인화 학습 정책을 사용하지 않는다. 기본 단축키는 ⌃⌥⇧Space이며 기존 세 조합을 보존한다. 선택한 Jev 연결이 필수이며 일반 자동 검토 설정과 독립적이다.

## 검증 현황

로컬의 전체 XCTest 시도는 Command Line Tools 환경의 XCTest 부재로 실행하지 못했다. 첫 일반 앱 빌드는 macOS 27 SDK의 SwiftUIMacros 플러그인 부재로 실패했으며, 저장소의 SDK preflight가 선택한 macOS 26.5 SDK로 최종 개발 앱 빌드와 strict ad-hoc 서명 검증이 통과했다. 최초 CI의 전체 938개 중 두 테스트에서 세 assertion이 실패했다. 기존 세 단축키 보존에 네 번째 조합을 추가하는 이주 기대값과, 접근 때마다 사전 UUID가 달라지는 테스트 fixture를 수정했다. 이전 리비전 `ddbfab9`의 CI에서 XCTest 951개(2개 건너뜀·실패 0개), Python 198개 전체와 개발 앱 빌드가 통과했다. 이후 추가한 계약 테스트 파일은 현재 생성 계약 31개, Jev 검토 14개, runner 13개, 플랫폼 흐름 6개로 합계 64개이며, 제공자 전송·빈 응답 분리 검사도 별도로 추가했다. 이는 현재 소스의 검사 수이며 최신 변경의 전체 XCTest 실행 성공을 뜻하지 않는다. 최신 리비전의 전체 XCTest·Python·개발 앱 빌드 결과는 [PR 검사 기록](https://github.com/techjuicelab/opennotype/pull/28/checks)에서 별도로 확인한다.

최초 Python 검증에서 새 prompt 의존성이 수동 Swift 소스 레지스트리에 빠져 세 평가 도구 테스트가 실패했다. `export-cleanup-prompts.py`와 `compare-decisions.py`의 소스 목록에 새 계약 파일을 추가했다. 수정 후 전체 Python 198개가 완료됐고 195개 통과, 환경 의존 3개는 건너뛰었다.

별도 미리보기 앱에서 홈의 프롬프트 카드, 기본 단축키, Jev 연결 미설정 안내, 코드·설계 제외와 생성/검토 횟수 안내를 화면으로 확인했다. 최종 결과 화면과 실제 마이크는 이 확인에 포함하지 않았다. 설치 앱은 교체하지 않았다.

독립 감사에서 기록 재처리를 시작하고 첫 비동기 작업이 재개되기 전에 제공자·모델을 바꾸면 이전 설정의 유료 처리가 시작될 수 있는 틈을 확인했다. 실제 프롬프트 작업 UUID를 시작 시점부터 추적해 취소하며, 마지막 녹음 모드가 프롬프트여도 일반 기록 재처리의 설정 캡처 동작은 유지한다. 두 동작에 회귀 테스트를 추가했다. 로컬 코드 문법 검사는 17개 거부/허용 사례를 실제 production 함수로 별도 확인했다.

## 실제 API 시험

개인 음성·기록을 사용하지 않고 합성 한국어 발화 세 개를 production Swift runner로 처리했다. 생성은 OpenRouter의 `openai/gpt-oss-120b`, 검토는 실제 Jev API를 사용했다. 각 사례는 생성 두 번·검토 두 번으로 제한하고 자동 재시도는 하지 않았다.

첫 시험에서 두 사례가 앱의 최종 검토를 통과했으나 모두 영어로 바뀌었으며, 하나는 기능 구현 요청을 다른 프롬프트 작성 요청으로 바꿨다. 나머지 사례는 초안에 잠정 API·DB·코드 조건 설계가 남고 최종 문장이 잘렸으며 앱이 보류했다. 이를 품질 통과로 집계하지 않는다. 이 결과를 바탕으로 원문 언어 hint, 실제 작업을 직접 요청하는 규칙, 잠정 설계도 배제하는 기준, 동작·음성 재응답 조건 보존을 보강했다. 코드·SQL·HTTP 설계 표기의 좁은 로컬 문법 차단도 생성 응답과 runner 양쪽에 연결했다.

1Password 인증 완료 후 두 차례 실제 API 재시험을 진행했다.

| 시험 | 앱 제공/보류 | 독립 검토 결과 |
| --- | --- | --- |
| 2차: 한국어 3개 | 1개 제공·2개 보류 | 한국어와 코드·설계 제외는 개선됐다. 기능 구현이 요청문 작성으로 바뀐 사례는 보류했고, 적절한 로그인 요청도 최종 pass 확률 0.79로 기준 0.8에 못 미쳐 보류했다. 제공한 게임 사례에는 선택적 오프라인 희망이 빠지고 추후 결정 약속이 생겼다. |
| 3차: 한국어 3개·영어 1개 | 3개 제공·1개 보류 | 기능 구현 의도는 복구됐으나 Codex 이름 누락 사례는 보류했다. 로그인 사례는 코드·설계를 제거한 요구만 남겼고 영어도 유지됐다. 게임 사례는 초안의 음성 재응답이 다듬기에서 일반 답하기로 약해졌는데도 최종 검토를 통과했다. |
| 4차: 같은 한국어 3개·영어 1개 | 1개 제공·3개 보류 | 모든 후보에서 언어와 코드·직접 설계 제외를 유지했다. 게임의 음성 재응답 누락과 화면 제약 강화는 보류됐다. 기능 구현·Codex·브랜치·에이전트 수는 회복됐으나 프롬프트 제약의 적용 대상이 모호한 사례는 보류됐다. 내용상 적합해 보이는 로그인 요청도 intent 점수 때문에 보류됐다. 영어 사례는 통과한 초안 자체가 최종 검토·제공됐다. |
| 5차: 같은 한국어 3개·영어 1개 | 1개 제공·3개 보류 | 네 사례에서 언어와 코드·직접 설계 제외를 유지했다. 음성 재응답이 일반 입력으로 바뀐 게임 사례는 보류가 적절하다. OpenNoType 기능 구현 사례는 수신자·브랜치·에이전트 수·출력 제약을, 로그인 사례는 재로그인 없는 사용·보안 유지를 보존했으나 둘 다 검토 기준 미달로 보류됐다. 영어 사례는 희망과 미정 상태까지 보존해 제공됐다. |

따라서 제공 개수를 품질 통과 개수로 계산하지 않는다. 이를 바탕으로 기능 구현과 일회성 프롬프트 작성 구분, 명시된 수신자 직접 호명, 희망과 미정 상태 동시 보존, 설계 예시를 대체 요구 없이 삭제하는 허용 범위를 보강했다. 첫 검토를 통과한 초안은 다듬기의 불필요한 표현 변경으로 교체하지 않고, 유지한 초안 자체를 마지막 Jev 검토에 보낸다. 첫 검토가 불충분한 경우에만 다듬은 후보를 선택하며 마지막 검토 기준은 유지한다. 최종 보류 후 이전 초안으로 되돌아가 제공하지 않는다.

4차 결과 이후 GPT-OSS 120b/20b의 프롬프트 생성에만 추론 수준을 `medium`으로 올리고, Jev의 메타 요청 구분 문장이 다른 실패 조건까지 제한하는 듯 읽히지 않도록 범위를 명시했다. 요청 한도·시간 제한·최종 판정 임계값은 유지했다. OpenRouter·Groq의 두 OSS 모델과 초안/다듬기 단계, 오류 무재시도, 다른 모델 정책 보존을 확인하는 제공자 계약 테스트 세 개를 추가했다. 최신 코드의 로컬 개발 앱 빌드와 strict ad-hoc 서명 검증도 통과했다. 공식 [OpenRouter 추론 문서](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)와 [Groq 추론 문서](https://console.groq.com/docs/reasoning)를 확인했으며, 추론 강화의 품질 효과는 실제 시험 결과로 판단한다.

5차 전체 흐름 16개와 고정 원문/후보 검토 4개를 한 번의 인증·키 주입으로 실행했다. 고정 후보의 intent pass 확률은 문구 수정 전 0.75/0.70, 수정 후 0.77/0.81로 정책 통과 0/2에서 1/2가 됐다. 네 응답 모두 모든 축의 선택은 pass였으며 보류는 정책 임계값 미달이었다. 각 두 번뿐이고 반복 결과도 변하므로 문구 수정이나 medium의 인과적 품질 개선 또는 안정화를 주장하지 않는다. 5차는 생성 결함 한 건과 독립 검토상 과도한 보류 후보 두 건을 구분해 기록한다.

## 음성 동작 보존과 검토 축 분리

후속 보강은 네 하위 에이전트가 생성 계약, JEV 질문, 독립 비교 세트, 수동·기록·UI 경로를 나누어 검토했다. 말하기·타이핑·클릭은 제거할 설계가 아니라 유지할 동작 요구임을 명시했다. 일반 입력·응답·재시도로 축약하거나 각 동작에 붙은 부정·조건의 범위를 바꾸지 않도록 초안과 다듬기 계약을 보강했다.

JEV 전용 네 질문은 의미 변형·임의 추가 및 설계·필수 내용 누락·하네스 침해로 나눴다. 긴 전체 정책을 모든 질문에 반복하던 구조에서, 각 질문에 공통 데이터 경계와 해당 축의 조건만 보낸다. 질문 instruction은 약 1.0–1.5KB다. 임계값, 응답 파서, 질문 수와 직렬화 순서는 유지했다. 공식 [Jev 1.13 알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)의 직접적인 조건과 일관된 기준 권고를 참고했지만, 이 문서만으로 현재 API 별칭의 정확한 버전이나 개선 효과를 확정하지 않는다.

독립 감사에서 기록의 수동 재검토는 상세 축을 끄면 기본 Noul 질문 세 개만 보내므로 전용 질문에만 경계를 옮기면 보호 규칙이 빠질 수 있음을 확인했다. 수동·기록 검토에는 별도 선언형 정책을 연결해 전체 경계를 유지한다. Noul에 Choice의 pass/fail 지시나 다른 축만 판단하라는 지시를 넣지 않는다. 양 제공자와 상세 검토 사용·미사용 요청의 실제 본문을 검사하도록 회귀 테스트를 보강했다.

[독립 합성 비교 세트](../../fixtures/prompt-composition-review.json)는 적합 8개·부적합 8개다. 원문 구현 예시의 요구사항 추상화, 기능 구현과 일회성 요청 구분, 음성·타이핑·클릭, 선택적 희망, 숫자·부정·언어와 하네스 경계를 포함한다. 기대 판정은 독립 의미 검토의 근거이며 모델 정답률이나 확률 보정 자료로 일반화하지 않는다. 같은 세트를 이전·후보 정책에서 각각 두 번 평가하고, 기존 네 사례에 네 동작·언어 변형을 추가한 전체 흐름을 별도로 시험하도록 준비했다. 최대 96개 요청을 한 번의 인증·실행에 묶으며 자동 재시도하지 않는다.

후속 코드의 로컬 개발 앱 빌드와 strict ad-hoc 서명 검증, 양 제공자의 비교 세트 요청 사전 검증을 통과한 뒤 아래 6차 배치를 실행했다.

이 배치에서 후보 정책은 부적합 후보를 통과시키지 않았지만 적합 후보의 통과도 한 건 줄었다. 이전 정책이 두 번 통과시킨 일반 입력으로 바뀐 음성 재응답 후보는 후보 정책에서 두 번 보류했다. 반면 요구사항만 남긴 적합한 로그인 후보는 후보 정책에서 두 번 보류했다. 따라서 이를 전반적인 정확도 개선이나 안정화로 단정하지 않는다. 동일 후보를 두 번씩만 평가했으며 결과와 임계값은 미보정 상태다.

전체 생성 흐름은 한국어·영어와 말하기·타이핑·클릭·조건·언어 지시를 포함한 합성 발화 8개를 별도로 처리했다. 5개는 완성 결과로 제공했고 3개는 보류했다. 두 사례는 의미 있는 원문이 있었지만 첫 생성 결과가 비어 후보·Jev 검토 없이 중단됐다. 다른 한 사례는 영어 원문에서 요청문을 한국어로 작성하라고 명시했으나 초안이 영어였고 원문에 없는 수신 AI 이름까지 들어갔다. 다듬은 후보는 한국어가 됐지만 수신자 발명은 남았으며 완성 결과는 보류했다. 제공 5개를 독립 품질 통과 5개나 정확도 5/8로 계산하지 않는다.

전체 흐름은 조기 중단 두 건 때문에 26개 요청을 사용했다. 비교 검토 64개와 합쳐 실제 요청은 **90개**, 제공자 사용량에서 관측한 비용 합계는 **USD 0.01335357**이었다. 이 비용은 해당 합성 원문·후보·모델·한 배치의 값이며 제품 사용 비용의 고정 견적이 아니다. 로컬 결과는 `build/voice-prompt-smoke/round6-results.json`, `round6-balanced-baseline.json`, `round6-balanced-candidate.json`과 소스 hash·호출 수를 담은 `round6-provenance.json`에 보관했다.

## 6차 이후 수정과 남은 검증

원문에 없는 수신자와 공유 예시의 수신자가 같았으므로 예시 오염 가능성을 검토했다. 단일 배치로 인과를 확정할 수는 없다. 생성 지침과 공유 예시에서 특정 수신 AI 고유명을 제거하고, 원문에 명시한 수신자만 직접 호명해 보존하도록 정리했다. 언어 우선순위도 생성 프롬프트의 명시 언어 요청 → 감지한 원문 언어 hint → 원문 주언어로 한곳에서 정의했다. 언어 지시는 상대 AI에게 다시 번역하라고 붙이지 않고 현재 결과 전체에 적용한다.

의미 있는 목표·요청·희망·문제가 있으면 미정 사항이나 코드·설계 언급 때문에 빈 결과를 반환하지 않도록 생성 계약을 명확히 했다. 빈 결과 예외는 의미 있는 의도가 전혀 없는 발화에만 허용한다. 이 지침이 실제 빈 생성 빈도를 줄였다는 검증은 아직 없다.

별도로 프롬프트 생성의 빈 `text`는 `PromptCompositionFailure.invalidOutput`으로 처리해 “생성된 프롬프트가 비어 있거나 형식 또는 길이를 확인하지 못했습니다”라고 안내하도록 수정했다. 앞선 배치에서 음성 인식 원문이 존재하는데도 “인식된 텍스트가 없음”으로 안내한 문제를 생성 응답 오류와 구분한 것이다. 기존 받아쓰기의 빈 결과 정책은 유지하며, 제공자·초안/다듬기별 빈 응답과 다른 모드의 기존 동작을 검사하는 회귀 테스트를 추가했다.

최신 생성 계약은 Swift parse·diff 검사와 macOS 26.5 SDK 개발 앱 빌드·strict ad-hoc 서명 검증을 통과했다. 리비전 `836fcca`의 CI에서 XCTest 970개 중 2개 건너뜀·실패 0을 확인했다. Python 검사는 모델 비교 도구의 독립 컴파일에서 새 공통 오류 타입을 찾지 못해 실패했다. `PromptCompositionFailure`를 공개 API와 오류 문구 변경 없이 공유 계약 파일로 옮겨 runner 의존성을 제거했고, 실패를 재현한 단일 Python 파일의 20개 검사가 통과했다. 이어 로컬 전체 Python 198개 중 환경 의존 3개 건너뜀·실패 0, 개발 앱 빌드·strict ad-hoc 서명 검증을 확인했다. 최신 전체 검증 결과는 [PR 검사 기록](https://github.com/techjuicelab/opennotype/pull/28/checks)에서 별도로 확인한다. 이 수정 이후의 최종 실제 API 배치는 아직 완료되지 않았다. 미완료 배치나 비용을 확인하지 못한 요청을 위 6차 관측치와 합산하지 않는다. 코드·직접 설계 제외, 자동 재시도 금지, 정상 완료 시 생성 2회·검토 2회, 기존 크기·시간 한도와 최종 검토 기준은 유지했다. 후속 실제 시험과 최종 CI 결과를 PR에 함께 기록한다.

최종 비교 세트에는 영어 원문의 명시 한국어 요청에 대해 적합·부적합 회귀 후보 두 개를 추가했다. 현재 합계는 적합 9개·부적합 9개이며, 추가 두 개는 6차의 관측 실패에서 파생됐다. 정책 보강에 사용한 사례이므로 독립 holdout 또는 미관측 일반화 검증으로 취급하지 않는다. 기대 실패 축은 최소 알려진 문제를 기술하며, 음성 동작 약화를 intent 또는 omissions에서 잡는 차이는 최종 오통과 여부와 따로 분석한다. 이 전용 네 Choice 질문의 결과를 별도 수동 검토의 세 Noul 질문 성능으로 일반화하지 않는다.

최종 배치의 이전 정책 비교 36회 중 34회는 응답이 저장됐다. 진행 로그의 출력 지연을 인증 대기로 잘못 판단해 실행을 중단했으며, 남은 비교와 전체 흐름 시험은 저장된 결과를 건너뛰어 재개하도록 준비했다. 중단 시 최대 한 개의 요청이 진행 중이었을 수 있어 비용이 미확인이다. 미완료 최종 배치의 응답·비용을 완료된 6차 결과와 합산하거나 전체 결과로 보고하지 않는다.

생성 계약 문자열 검사와 모의 공급자 테스트는 실제 모델의 의미 보존이나 코드·설계 배제 성공률을 입증하지 않는다. 어떤 모델·언어·발화에서나 동일한 품질을 보장하지 않으며, 대상 AI 앱에 직접 붙여넣어 실행하는 시험은 하지 않았다. 후속 실제 시험과 CI 결과는 [초안 PR #28](https://github.com/techjuicelab/opennotype/pull/28)에 함께 기록한다.
