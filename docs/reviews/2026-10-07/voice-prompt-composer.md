# 음성 작업 프롬프트 개발 기록

2026-10-07, `main`의 `f8a2adf`에서 새 브랜치 `codex/voice-prompt-composer`를 만들었다. 기존 받아쓰기·번역과 별도로, 불규칙한 발화를 코드나 직접 설계가 없는 간결한 요구사항 프롬프트로 변환한다. 공개 릴리스·설치 앱 교체는 이 작업에 포함하지 않았다.

## 분담과 구현

| 담당 | 범위 |
| --- | --- |
| 에이전트 1 | 프롬프트 생성·최종 다듬기 계약, 설정 분리, 코드·설계 제외 지침과 테스트 |
| 에이전트 2 | 공식 API 확인, Jev 4축 검토·엄격한 파서·목적별 기록 검토 |
| 에이전트 3 | 홈·메뉴·결과 복사 화면, 네 번째 단축키와 기존 설정 이주 |
| 에이전트 4 | 독립 통합 감사, runner 호출 순서·실패·취소·크기 한도 회귀 테스트 |
| 통합 담당 | 음성·복구·기록 다시 처리 연결, 수명/취소, 사용량, 문서와 빌드 검증 |

실행 슬롯 제한에 따라 1~3 담당을 먼저 시작하고 UI 완료 뒤 네 번째 담당을 투입했다. 새 채팅 네 개를 만든 것이 아니라 현재 작업의 하위 에이전트 네 개를 사용했다.

초안과 최종 결과는 각각 독립 Jev 검토를 거친다. 최종 통과는 네 축 모두 pass probability ≥0.8 및 confidence ≥0.6일 때다. 이 임계값은 미보정 제품 정책이며 정확도 백분율이 아니다. 실패·불확실·잘못된 응답은 완성 결과로 제공하지 않는다. 첫 검토의 고정 문제 유형만 한 번의 최종 다듬기에 전달한다. 상대 AI가 쓸 코드나 설계·도구 흐름을 생성하지 않는다.

최종 결과는 복사 전용이며 외부 앱 입력·AI 제출을 실행하지 않는다. `InputMode.prompt`는 기존 언어/표현·번역·개인화 학습 정책을 사용하지 않는다. 기본 단축키는 ⌃⌥⇧Space이며 기존 세 조합을 보존한다. 선택한 Jev 연결이 필수이며 일반 자동 검토 설정과 독립적이다.

## 검증 현황

로컬의 전체 XCTest 시도는 Command Line Tools 환경의 XCTest 부재로 실행하지 못했다. 첫 일반 앱 빌드는 macOS 27 SDK의 SwiftUIMacros 플러그인 부재로 실패했으며, 저장소의 SDK preflight가 선택한 macOS 26.5 SDK로 최종 개발 앱 빌드와 strict ad-hoc 서명 검증이 통과했다. 최초 CI의 전체 938개 중 두 테스트에서 세 assertion이 실패했다. 기존 세 단축키 보존에 네 번째 조합을 추가하는 이주 기대값과, 접근 때마다 사전 UUID가 달라지는 테스트 fixture를 수정했다. 이전 리비전 `ddbfab9`의 CI에서 XCTest 951개(2개 건너뜀·실패 0개), Python 198개 전체와 개발 앱 빌드가 통과했다. 이후 추가한 계약 테스트 파일은 현재 생성 계약 36개, Jev 검토 15개, runner 13개, 플랫폼 흐름 6개로 합계 70개이며, 제공자 전송·빈 응답 분리 검사도 별도로 추가했다. 이는 현재 소스의 검사 수이며 최신 변경의 전체 XCTest 실행 성공을 뜻하지 않는다. 최신 리비전의 전체 XCTest·Python·개발 앱 빌드 결과는 [PR 검사 기록](https://github.com/techjuicelab/opennotype/pull/28/checks)에서 별도로 확인한다.

최초 Python 검증에서 새 prompt 의존성이 수동 Swift 소스 레지스트리에 빠져 세 평가 도구 테스트가 실패했다. `export-cleanup-prompts.py`와 `compare-decisions.py`의 소스 목록에 새 계약 파일을 추가했다. 수정 후 전체 Python 198개가 완료됐고 195개 통과, 환경 의존 3개는 건너뛰었다.

별도 미리보기 앱에서 홈의 프롬프트 카드, 기본 단축키, Jev 연결 미설정 안내, 코드·설계 제외와 생성/검토 횟수 안내를 화면으로 확인했다. 최종 결과 화면과 실제 마이크는 이 확인에 포함하지 않았다. 설치 앱은 교체하지 않았다.

독립 감사에서 기록 재처리를 시작하고 첫 비동기 작업이 재개되기 전에 제공자·모델을 바꾸면 이전 설정의 유료 처리가 시작될 수 있는 틈을 확인했다. 실제 프롬프트 작업 UUID를 시작 시점부터 추적해 취소하며, 마지막 녹음 모드가 프롬프트여도 일반 기록 재처리의 설정 캡처 동작은 유지한다. 두 동작에 회귀 테스트를 추가했다. 로컬 코드 문법 검사는 17개 거부/허용 사례를 실제 production 함수로 별도 확인했다.

## 실제 API 시험

개인 음성·기록을 사용하지 않고 합성 한국어 발화 세 개를 production Swift runner로 처리했다. 생성은 OpenRouter의 `openai/gpt-oss-120b`, 검토는 실제 Jev API를 사용했다. 각 사례는 생성 두 번·검토 두 번으로 제한하고 자동 재시도는 하지 않았다.

첫 시험에서 두 사례가 앱의 최종 검토를 통과했으나 모두 영어로 바뀌었으며, 하나는 기능 구현 요청을 다른 프롬프트 작성 요청으로 바꿨다. 나머지 사례는 초안에 잠정 API·DB·코드 조건 설계가 남고 최종 문장이 잘렸으며 앱이 보류했다. 이를 품질 통과로 집계하지 않는다. 이 결과를 바탕으로 원문 언어 hint, 실제 작업을 직접 요청하는 규칙, 잠정 설계도 배제하는 기준, 동작·음성 재응답 조건 보존을 보강했다. 코드·SQL·HTTP 설계 표기의 좁은 로컬 문법 차단도 생성 응답과 runner 양쪽에 연결했다.

1Password 인증 완료 후 두 차례 실제 API 재시험을 진행했다.

| 시험 | 앱 제공/보류 | 독립 검토 결과 |
| --- | --- | --- |
| 2차: 한국어 3개 | 1개 제공·2개 보류 | 한국어와 코드·설계 제외는 개선됐다. 기능 구현이 요청문 작성으로 바뀐 사례는 보류했고, 적절한 로그인 요청도 최종 pass 확률 0.79로 기준 0.8에 못 미쳐 보류했다. 제공한 게임 사례에는 선택적 오프라인 희망이 빠지고 추후 결정 약속이 생겼다. |
| 3차: 한국어 3개·영어 1개 | 3개 제공·1개 보류 | 기능 구현 의도는 복구됐으나 Codex 이름 누락 사례는 보류했다. 로그인 사례는 코드·설계를 제거한 요구만 남겼고 영어도 유지됐다. 게임 사례는 초안의 음성 재응답이 다듬기에서 일반 답하기로 약해졌는데도 최종 검토를 통과했다. |
| 4차: 같은 한국어 3개·영어 1개 | 1개 제공·3개 보류 | 모든 후보에서 언어와 코드·직접 설계 제외를 유지했다. 게임의 음성 재응답 누락과 화면 제약 강화는 보류됐다. 기능 구현·Codex·브랜치·에이전트 수는 회복됐으나 프롬프트 제약의 적용 대상이 모호한 사례는 보류됐다. 내용상 적합해 보이는 로그인 요청도 intent 점수 때문에 보류됐다. 영어 사례는 통과한 초안 자체가 최종 검토·제공됐다. |
| 5차: 같은 한국어 3개·영어 1개 | 1개 제공·3개 보류 | 네 사례에서 언어와 코드·직접 설계 제외를 유지했다. 음성 재응답이 일반 입력으로 바뀐 게임 사례는 보류가 적절하다. OpenNoType 기능 구현 사례는 수신자·브랜치·에이전트 수·출력 제약을, 로그인 사례는 재로그인 없는 사용·보안 유지를 보존했으나 둘 다 검토 기준 미달로 보류됐다. 영어 사례는 희망과 미정 상태까지 보존해 제공됐다. |

따라서 제공 개수를 품질 통과 개수로 계산하지 않는다. 이를 바탕으로 기능 구현과 일회성 프롬프트 작성 구분, 명시된 수신자 직접 호명, 희망과 미정 상태 동시 보존, 설계 예시를 대체 요구 없이 삭제하는 허용 범위를 보강했다. 첫 검토를 통과한 초안은 다듬기의 불필요한 표현 변경으로 교체하지 않고, 유지한 초안 자체를 마지막 Jev 검토에 보낸다. 첫 검토가 불충분한 경우에만 다듬은 후보를 선택하며 마지막 검토 기준은 유지한다. 최종 보류 후 이전 초안으로 되돌아가 제공하지 않는다.

4차 결과 이후 GPT-OSS 120b/20b의 프롬프트 생성에만 추론 수준을 `medium`으로 올리고, Jev의 메타 요청 구분 문장이 다른 실패 조건까지 제한하는 듯 읽히지 않도록 범위를 명시했다. 요청 한도·시간 제한·최종 판정 임계값은 유지했다. OpenRouter·Groq의 두 OSS 모델과 초안/다듬기 단계, 오류 무재시도, 다른 모델 정책 보존을 확인하는 제공자 계약 테스트 세 개를 추가했다. 최신 코드의 로컬 개발 앱 빌드와 strict ad-hoc 서명 검증도 통과했다. 공식 [OpenRouter 추론 문서](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens)와 [Groq 추론 문서](https://console.groq.com/docs/reasoning)를 확인했으며, 추론 강화의 품질 효과는 실제 시험 결과로 판단한다.

5차 전체 흐름 16개와 고정 원문/후보 검토 4개를 한 번의 인증·키 주입으로 실행했다. 고정 후보의 intent pass 확률은 문구 수정 전 0.75/0.70, 수정 후 0.77/0.81로 정책 통과 0/2에서 1/2가 됐다. 네 응답 모두 모든 축의 선택은 pass였으며 보류는 정책 임계값 미달이었다. 각 두 번뿐이고 반복 결과도 변하므로 문구 수정이나 medium의 인과적 품질 개선 또는 안정화를 주장하지 않는다. 5차는 생성 결함 한 건과 독립 검토상 과도한 보류 후보 두 건을 구분해 기록한다.

## 음성 동작 보존과 검토 축 분리

후속 보강은 네 하위 에이전트가 생성 계약, JEV 질문, 독립 비교 세트, 수동·기록·UI 경로를 나누어 검토했다. 말하기·타이핑·클릭은 제거할 설계가 아니라 유지할 동작 요구임을 명시했다. 일반 입력·응답·재시도로 축약하거나 각 동작에 붙은 부정·조건의 범위를 바꾸지 않도록 초안과 다듬기 계약을 보강했다.

JEV 전용 네 질문은 의미 변형·임의 추가 및 설계·필수 내용 누락·하네스 침해로 나눴다. 긴 전체 정책을 모든 질문에 반복하던 구조에서, 각 질문에 공통 데이터 경계와 해당 축의 조건만 보낸다. 각 질문에는 공통 데이터 경계와 해당 축의 조건만 포함한다. 임계값, 응답 파서, 질문 수와 직렬화 순서는 유지했다. 공식 [Jev 1.13 알려진 한계](https://docs.typesafe.ai/model-jaggedness/jev-1.13)의 직접적인 조건과 일관된 기준 권고를 참고했지만, 이 문서만으로 현재 API 별칭의 정확한 버전이나 개선 효과를 확정하지 않는다.

독립 감사에서 기록의 수동 재검토는 상세 축을 끄면 기본 Noul 질문 세 개만 보내므로 전용 질문에만 경계를 옮기면 보호 규칙이 빠질 수 있음을 확인했다. 수동·기록 검토에는 별도 선언형 정책을 연결해 전체 경계를 유지한다. Noul에 Choice의 pass/fail 지시나 다른 축만 판단하라는 지시를 넣지 않는다. 양 제공자와 상세 검토 사용·미사용 요청의 실제 본문을 검사하도록 회귀 테스트를 보강했다.

6차 당시 [합성 비교 세트](../../fixtures/prompt-composition-review.json)는 적합 8개·부적합 8개였다(링크의 현재 파일에는 후속 회귀쌍이 추가됐다). 원문 구현 예시의 요구사항 추상화, 기능 구현과 일회성 요청 구분, 음성·타이핑·클릭, 선택적 희망, 숫자·부정·언어와 하네스 경계를 포함한다. 기대 판정은 독립 의미 검토의 근거이며 모델 정답률이나 확률 보정 자료로 일반화하지 않는다. 같은 세트를 이전·후보 정책에서 각각 두 번 평가하고, 기존 네 사례에 네 동작·언어 변형을 추가한 전체 흐름을 별도로 시험하도록 준비했다. 최대 96개 요청을 한 번의 인증·실행에 묶으며 자동 재시도하지 않는다.

후속 코드의 로컬 개발 앱 빌드와 strict ad-hoc 서명 검증, 양 제공자의 비교 세트 요청 사전 검증을 통과한 뒤 아래 6차 배치를 실행했다.

이 배치에서 후보 정책은 부적합 후보를 통과시키지 않았지만 적합 후보의 통과도 한 건 줄었다. 이전 정책이 두 번 통과시킨 일반 입력으로 바뀐 음성 재응답 후보는 후보 정책에서 두 번 보류했다. 반면 요구사항만 남긴 적합한 로그인 후보는 후보 정책에서 두 번 보류했다. 따라서 이를 전반적인 정확도 개선이나 안정화로 단정하지 않는다. 동일 후보를 두 번씩만 평가했으며 결과와 임계값은 미보정 상태다.

전체 생성 흐름은 한국어·영어와 말하기·타이핑·클릭·조건·언어 지시를 포함한 합성 발화 8개를 별도로 처리했다. 5개는 완성 결과로 제공했고 3개는 보류했다. 두 사례는 의미 있는 원문이 있었지만 첫 생성 결과가 비어 후보·Jev 검토 없이 중단됐다. 다른 한 사례는 영어 원문에서 요청문을 한국어로 작성하라고 명시했으나 초안이 영어였고 원문에 없는 수신 AI 이름까지 들어갔다. 다듬은 후보는 한국어가 됐지만 수신자 발명은 남았으며 완성 결과는 보류했다. 제공 5개를 독립 품질 통과 5개나 정확도 5/8로 계산하지 않는다.

전체 흐름은 조기 중단 두 건 때문에 26개 요청을 사용했다. 비교 검토 64개와 합쳐 실제 요청은 **90개**, 제공자 사용량에서 관측한 비용 합계는 **USD 0.01335357**이었다. 이 비용은 해당 합성 원문·후보·모델·한 배치의 값이며 제품 사용 비용의 고정 견적이 아니다. 로컬 결과는 `build/voice-prompt-smoke/round6-results.json`, `round6-balanced-baseline.json`, `round6-balanced-candidate.json`과 소스 hash·호출 수를 담은 `round6-provenance.json`에 보관했다.

## 6차 이후 수정과 남은 검증

원문에 없는 수신자와 공유 예시의 수신자가 같았으므로 예시 오염 가능성을 검토했다. 단일 배치로 인과를 확정할 수는 없다. 생성 지침과 공유 예시에서 특정 수신 AI 고유명을 제거하고, 원문에 명시한 수신자만 직접 호명해 보존하도록 정리했다. 언어 우선순위도 생성 프롬프트의 명시 언어 요청 → 감지한 원문 언어 hint → 원문 주언어로 한곳에서 정의했다. 언어 지시는 상대 AI에게 다시 번역하라고 붙이지 않고 현재 결과 전체에 적용한다.

의미 있는 목표·요청·희망·문제가 있으면 미정 사항이나 코드·설계 언급 때문에 빈 결과를 반환하지 않도록 생성 계약을 명확히 했다. 빈 결과 예외는 의미 있는 의도가 전혀 없는 발화에만 허용한다. 7차의 같은 합성 발화 8개에서는 빈 생성이 없었지만, 한 배치로 빈 생성 빈도의 일반적인 개선을 주장하지 않는다.

별도로 프롬프트 생성의 빈 `text`는 `PromptCompositionFailure.invalidOutput`으로 처리해 “생성된 프롬프트가 비어 있거나 형식 또는 길이를 확인하지 못했습니다”라고 안내하도록 수정했다. 앞선 배치에서 음성 인식 원문이 존재하는데도 “인식된 텍스트가 없음”으로 안내한 문제를 생성 응답 오류와 구분한 것이다. 기존 받아쓰기의 빈 결과 정책은 유지하며, 제공자·초안/다듬기별 빈 응답과 다른 모드의 기존 동작을 검사하는 회귀 테스트를 추가했다.

최신 생성 계약은 Swift parse·diff 검사와 macOS 26.5 SDK 개발 앱 빌드·strict ad-hoc 서명 검증을 통과했다. 리비전 `836fcca`의 CI에서 XCTest 970개 중 2개 건너뜀·실패 0을 확인했다. Python 검사는 모델 비교 도구의 독립 컴파일에서 새 공통 오류 타입을 찾지 못해 실패했다. `PromptCompositionFailure`를 공개 API와 오류 문구 변경 없이 공유 계약 파일로 옮겨 runner 의존성을 제거했고, 실패를 재현한 단일 Python 파일의 20개 검사가 통과했다. 이어 로컬 전체 Python 198개 중 환경 의존 3개 건너뜀·실패 0, 개발 앱 빌드·strict ad-hoc 서명 검증을 확인했다. 소스 리비전 `025f3e4`의 [PR CI](https://github.com/techjuicelab/opennotype/actions/runs/37707018990)와 [push CI](https://github.com/techjuicelab/opennotype/actions/runs/37707015671)는 모두 통과했다. XCTest 970개 중 2개 건너뜀·실패 0, Python 198개 전체 통과, 개발 앱 빌드·strict ad-hoc 서명 검증·아티팩트 업로드를 확인했다. 이후 실제 API 배치는 아래 7차에서 완료했다. 코드·직접 설계 제외, 자동 재시도 금지, 정상 완료 시 생성 2회·검토 2회, 기존 크기·시간 한도와 최종 검토 기준은 유지했다. 후속 실제 시험과 최종 CI 결과를 PR에 함께 기록한다.

7차 비교 세트에는 영어 원문의 명시 한국어 요청에 대해 적합·부적합 회귀 후보 두 개를 추가했다. 당시 합계는 적합 9개·부적합 9개였으며, 추가 두 개는 6차의 관측 실패에서 파생됐다. 정책 보강에 사용한 사례이므로 독립 holdout 또는 미관측 일반화 검증으로 취급하지 않는다. 기대 실패 축은 최소 알려진 문제를 기술하며, 음성 동작 약화를 intent 또는 omissions에서 잡는 차이는 최종 오통과 여부와 따로 분석한다. 이 전용 네 Choice 질문의 결과를 별도 수동 검토의 세 Noul 질문 성능으로 일반화하지 않는다.

## 7차 일괄 인증 재개와 독립 검토

이전 정책의 36회 검토 중 34회 저장 뒤 진행 로그 출력 지연을 인증 대기로 잘못 판단해 중단했다. 이후 사용자 요청에 따라 한 번의 `op run`으로 저장된 34회를 건너뛰고 나머지 70개의 완료 응답을 추가 인증 없이 받았다. 비교 검토 36+36회와 전체 흐름 32회를 합쳐 완료 응답·사용량 기록은 104개다. 이전 중단 시 최대 한 개의 미기록 요청이 진행 중이었을 수 있어, 이 수치를 전체 HTTP 시도 횟수나 전체 청구액으로 확정하지 않는다.

| 세트 | 정책 | 적합 후보 정책 통과 | 부적합 후보 정책 통과 |
| --- | --- | --- | --- |
| 기존 16개 × 2회 | 이전 `635ecf3` | 11/16 | 2/16 |

72개 비교 응답은 모두 계약상 valid이며 중복·누락 없이 원문·후보·통과 계산이 일치했다. 후보의 적합 보류 8개 측정은 네 축 모두 선택값이 pass였지만 확률 또는 confidence가 정책 기준에 못 미쳤다. 낮은 점수로 보류했다는 사실을 오류를 정확히 분류한 결과로 세지 않는다. 기존 음성 재응답 약화 후보의 오통과는 막았지만 정상 후보의 과도한 보류가 남아 전체 정확도 개선으로 단정할 수 없다.

전체 생성 흐름은 8개 중 6개 제공·2개 보류였다. 제공된 6개 모두 코드·의사코드·직접 설계 잔존은 발견하지 못했다. 다만 수량 입력의 실제 제공문은 타이핑 전용 요구 뒤에 “숫자를 클릭하거나 음성 입력을 비활성화”라고 써, 클릭하라는 지시로도 읽히는 부정 범위 결함이 있었다. 두 JEV 검토 모두 이를 통과시켰으므로 제공 수를 의미 정답 수로 계산하지 않는다. 게임 사례는 실제 제공 초안이 음성 재응답·같은 문제·오프라인 희망/미정을 보존했으나 화면의 복잡도를 늘리지 말라는 조건을 단순하게 유지하라는 표현으로 강화할 여지가 있다. 오프라인 요구가 빠진 다듬기 후보는 제공하지 않았다.

OpenNoType 사례는 간접 위임 초안과 잘린 다듬기 후보 때문에 보류가 타당했다. 영어 원문에서 한국어 요청을 명시한 사례는 한국어 본문·음성 교정·확인 전 원본 보존을 회복했지만 intent pass 확률 0.67·confidence 0.51로 최종 보류했다. 일반명사를 “Notes 앱”으로 옮긴 표현에는 고유 제품명으로 읽힐 여지도 있다. 이를 명백한 잘못된 출력을 성공적으로 차단한 사례로 집계하지 않는다.

관측 비용은 baseline USD 0.009475536 + candidate USD 0.003247608 + 전체 흐름 USD 0.002880942 = **USD 0.015604086**이다. 기록된 104개 응답의 비용 누락은 없지만 이전 중단 중 최대 한 개의 미기록 요청 비용은 제외됐다. 비교 검토 72개가 보고한 모델은 모두 `typesafe/jev-1.13-20260917`이다. 생성 모델은 driver에 설정된 `openai/gpt-oss-120b`이며 이 배치의 main JSON에는 실제 보고 모델명을 따로 저장하지 않았다. 소스 SHA는 `025f3e4`, 이전 검토 두 파일은 `635ecf3`와 일치한다. 결과·소스 hash는 로컬 `build/voice-prompt-smoke/round7-*.json`에 보존했다.

후속 보강은 복수 금지의 명시적 범위, 상대적 제약의 강화 금지, 일반 앱 명칭의 고유명 승격 방지, 문장 끝 잘림 표시의 거부로 한정했다. 임계값을 낮추거나 허용된 호출 수를 늘려 사례를 통과시키지 않았다.

## 8차 일괄 실행과 최종 품질 한계

모든 실행 파일을 먼저 컴파일하고 로컬 Python 198개(환경 의존 3개 건너뜀·실패 0), 개발 앱 빌드·strict ad-hoc 서명 검증을 마친 뒤 한 번의 `op run`으로 후속 배치를 실행했다. 이전 정책의 저장된 36회 측정을 그대로 재사용하고 신규 비교 44회와 전체 흐름 31회의 응답을 추가 인증 없이 받았다. 전체 흐름 한 건은 세 번째 요청의 응답 형식 거부로 중단했으며 자동 재시도하지 않았다.

7차 수량 입력 오류에서 파생한 적합·모호한 후보 두 개를 추가해 비교 세트는 적합 10개·부적합 10개가 됐다. 앞선 언어 회귀쌍과 이번 부정 회귀쌍은 모두 정책 보강에 사용한 관측 기반 사례이며 독립 holdout이 아니다. 이전 정책 `635ecf3`과 후보는 같은 고정 후보를 각각 두 번 검토했다.

| 세트 | 정책 | 적합 후보 정책 통과 | 부적합 후보 정책 통과 |
| --- | --- | --- | --- |
| 기존 16개 × 2회 | 이전 정책 | 11/16 | 2/16 |
| 기존 16개 × 2회 | 후보 정책 | 10/16 | 0/16 |

부정 범위가 모호하면 uncertain으로 보류하라는 지침을 추가했지만 실제 JEV는 해당 부적합 후보를 두 번 모두 통과시켰다. 생성 지침 보강과 검토기의 검출 능력을 구분하며, 이번 보강이 이 문제를 해결했다고 주장하지 않는다.

전체 생성 흐름은 8개 중 5개 제공·3개 보류였다. 제공된 5개에 코드·직접 설계 잔존은 발견하지 못했지만 독립 의미 검토에서 두 결함과 한 가지 해석 위험을 확인했다. 영어 기능 요청은 해당 프로젝트의 오프라인 희망·미정을 모든 희망을 optional/undecided로 보존하는 제품 규칙으로 일반화했다. 예약 요청은 음성 날짜·시간 입력과 확인 전 확정 금지를 남겼지만 명시된 “키보드로 치지 않고”를 누락했다. 게임 요청은 재응답 기회를 “다시 말하도록”으로 옮겨 행동 요구로 읽힐 여지가 있다. 이들을 모두 JEV가 최종 통과시켰으므로 의도 보존은 보장되지 않는다.

수량 입력의 실제 제공문은 “숫자를 클릭하거나 음성으로 입력하는 옵션은 제공하지 마세요”로 공통 부정의 범위가 명확해졌다. 다만 제공하지 않은 다듬기 후보에는 모호한 부정 범위가 다시 나타났다. 공유 요청은 승인 후 클릭·자동 공유 금지를 보존했다. 두 적합 사례의 관측이며 일반적인 성공률이나 JEV의 검출 개선을 입증하지 않는다. 제공 5개를 의미 정답 5개로 계산하지 않는다.

OpenNoType 초안은 명시된 Codex 수신자를 누락했고 에이전트 표기가 손상됐다. 다듬기 응답은 형식 거부로 중단했으며 원문을 저장하지 않았으므로 말줄임표·코드·다른 형식 중 무엇이 원인이었는지 확정하지 않는다. 로그인 후보는 재로그인 없는 사용과 보안 유지를 보존한 내용상 적합한 문장이었지만 마지막 intent 0.79·omissions 0.77로 보류됐다. 한국어로 작성하라는 영어 원문 사례는 무의미한 초안을 적절히 거부한 뒤, 한국어 본문·음성 교정·확인 전 원본 보존을 갖춘 다듬기 후보도 intent 0.67·confidence 0.51로 보류했다. 적합 후보의 과도한 보류가 남았다.

기록된 응답·사용량은 재사용 36개를 포함해 **111개**, 관측 비용 합계는 **USD 0.017122988**이다. 이번에 새로 완료한 **75개**의 비용은 **USD 0.007647452**이며 재사용 비용을 중복 합산하지 않았다. 과거 중단 중 최대 한 개의 미기록 요청 비용은 포함하지 않으므로 전체 청구액으로 단정하지 않는다. 생성 16개 응답의 실제 보고 모델은 `openai/gpt-oss-120b`, 검토 응답은 `typesafe/jev-1.13-20260917`이다. 생성 사용량의 보고 reasoningTokens는 모두 0이고 출력 토큰은 8~66으로, 이 자료에서 4,096토큰 한도 소진을 실패 원인으로 추정할 근거는 없다. 요청 설정의 medium과 제공자가 보고한 추론 사용량도 구분한다.

결과·비교 세트·소스 hash·사용량·모델명은 로컬 `build/voice-prompt-smoke/round8-*.json`에 보존했다. 생성과 JEV의 불확실성이 남아 초안 PR을 유지하며 설치·릴리스·대상 AI 자동 실행은 하지 않았다. 최신 변경의 전체 CI는 [PR 검사 기록](https://github.com/techjuicelab/opennotype/pull/28/checks)에 연결한다.

## 별도 테스트 설치본 준비

사용자가 기존 앱과 구별되는 테스트 설치본을 요청해 `app.opennotype.prompt-test` 식별자의 `OpenNoType Prompt Test` 패키징을 추가했다. UI·패키징·저장소 분리·독립 감사에 네 전문 에이전트를 분담했다. 이름만 바꾸면 고정된 Keychain service와 Application Support 경로를 공유하는 문제를 발견해 설정뿐 아니라 API 키·암호화 기록·실패 녹음·학습·사용량·Whisper/화자 모델·임시 녹음도 별도로 연결했다. 정상 앱과 nil/unknown identity는 기존 경로·서비스를 유지한다.

메뉴바에는 `TEST`, 창·메뉴에는 테스트 이름을 표시한다. 실제 앱 모델과 네트워크 경로를 사용하며 usage-preview의 합성 모델은 사용하지 않는다. Space 기반의 정상 앱 단축키와 구별되는 `⌃⌥⌘D/T/R/P` 기본값을 주고, 업데이트 feed와 공개 키를 제거해 Sparkle backend를 생성하지 않는다. 설치된 다른 앱이나 실행 중인 테스트 앱을 빌드 스크립트로 덮어쓰지 않는다. CI에서 일반 개발 앱과 테스트 앱을 각각 패키징해 별도 아티팩트로 보관한다.

테스트 앱 최초 설정은 명시적인 테스트 전용 실행 인자에서만 1Password가 환경으로 주입한 Groq·OpenRouter 키를 테스트 Keychain에 등록한다. 두 값 모두 검증한 뒤 누락된 항목만 등록하며 이미 저장된 테스트 키는 유지한다. 정상 앱에서는 해당 경로를 실행하지 않고, 기존 앱의 Keychain 키를 읽어 복사하지 않는다. 주입 변수는 등록 후 제거하며 키 값을 인자·파일·로그에 쓰지 않는다.

로컬에서 테스트 패키징·arm64 실행 파일·별도 ID·메뉴바 전용 정책·업데이트 제거·strict 코드 서명을 확인했다. 설정 도메인, provider 키 조회/삭제, 암호키 fallback 금지, 모델 경로, 단축키 등록, 표시명, 배치 키 등록과 설정 복구에 회귀 테스트를 추가했다. 실제 설치·실행·권한 상태와 최신 전체 CI 결과는 PR에 별도로 기록한다. 마이크 발화의 품질이나 기존 JEV의 의미 검토 한계가 이 패키징으로 해결됐다는 뜻은 아니다.

생성 계약 문자열 검사와 모의 공급자 테스트는 실제 모델의 의미 보존이나 코드·설계 배제 성공률을 입증하지 않는다. 어떤 모델·언어·발화에서나 동일한 품질을 보장하지 않으며, 대상 AI 앱에 직접 붙여넣어 실행하는 시험은 하지 않았다. 후속 실제 시험과 CI 결과는 [초안 PR #28](https://github.com/techjuicelab/opennotype/pull/28)에 함께 기록한다.

## 실사용 보류와 확인 화면 보완

별도 테스트 앱에서 독서 기록 앱을 개선하려는 발화를 실제 마이크로 처리한 뒤 최종 보류된 사례가 보고됐다. 원문·초안은 시작하기 화면 하단에 남아 있었지만 다시 처리 화면에는 녹음만 표시됐고, 보류를 알리는 문구에서 확인 화면을 찾기 어려웠다. 초안에는 앱 기능 개선이 일회성 기록 정리로 읽히는 작업 수준 변화, 명시된 수신자와 기록의 문체 제약 누락, 알림 희망·미정의 축소가 있었다. 음성 인식에도 일부 오류가 있었다. 당시 최종 검토 후보와 판정 축은 화면에 전달되지 않았으므로 어느 항목이 실제 보류를 일으켰는지 단정하지 않는다.

실제 Runner를 호출하는 오프라인 합성 재현에서 첫 검토가 거절한 초안을 다듬어 최종 검토해도 진행 콜백은 원래 초안만 전달하고, 최종 판정은 보류 예외와 함께 소실됨을 확인했다. 최종 검토의 입력 후보를 정확히 전달하고 유효한 초안·최종 판정을 각각 화면용 메모리에 보유하도록 고쳤다. 작업·epoch·원문·후보를 대조한 뒤 게시하며 잘못된 검토 응답은 판정으로 게시하지 않는다. 보류 판정은 유지하고 승인 출력은 생성하지 않는다.

시작하기와 다시 처리에서 동일한 결과 패널로 원문·최종 검토 후보·검토의 네 축을 확인할 수 있다. 초안과 최종 후보가 같으면 중복 표시를 줄이며, 보류 때 확인 내용을 펼친다. 통과 신호·확신은 정확도가 아니며 통과 선택의 기준 미달도 구분한다. 화면용 자료를 영속화하지 않는 기존 정책과 실패 음성의 보관·만료는 유지한다. 생성 계약은 앱 사용 예시를 일회성 작업으로 바꾸지 않고 제품 출력의 문체 제약을 보존하도록 보강했다. 임계값·유료 호출 상한·자동 재시도 정책은 변경하지 않았다. 후속 실제 앱 재처리·CI 결과는 PR에 기록한다.
