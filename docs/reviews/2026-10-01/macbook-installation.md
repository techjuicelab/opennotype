# 새 Mac 설치에서 발견한 문제와 개선

2026-10-01, Apple M5 MacBook Pro 16 GB와 macOS 27.0에서 공개 0.1.10 앱의 최초 설치, 권한 설정, 입력 실패 진단, 수정 앱 교체를 진행했다. 개발 도구는 Command Line Tools의 Swift 6.4였다. 다음 내용은 이 한 기기에서 확인한 결과이며, 다른 모든 Mac의 성공을 뜻하지 않는다. 개선 소스의 다음 개발 버전은 0.1.12 (13)이다. 이 Mac에 설치해 검증한 앱은 0.1.11 (12)이며, 아래 빌드·설치 결과는 해당 버전의 기록이다. 공개 최신 다운로드 0.1.10을 변경하거나 새 릴리스를 공개한 상태는 아니다.

## 발견한 문제

| 사용자에게 보인 현상 | 확인된 원인 또는 범위 | 개선 |
| --- | --- | --- |
| 새 Mac에 앱이 없어 소스 빌드부터 시작하게 됨 | 일반 사용자가 필요로 하는 것은 배포 앱이며, Xcode·Swift·로컬 모델 다운로드가 설치의 필수 단계는 아님 | 배포 앱 설치와 개발자 빌드를 구분하고 검증된 배포 파일의 설치 경로를 제공 |
| 기본 개발 도구로 테스트·빌드 실패 | CLT에 XCTest가 없고 macOS 27 SDK의 SwiftUI macro plugin을 불러오지 못함. 설치되어 있던 macOS 26.5 SDK로 앱 빌드는 성공 | SDK 선택과 빌드 준비 상태를 사전 검사하고, 전체 XCTest에는 Xcode가 필요하다고 구분 |
| Xcode CI의 전체 테스트는 통과했지만 사전 검사에 XCTest 실패 경고가 표시됨 | 앱용 arm64 target을 테스트 검사에도 고정하고 Xcode의 developer Swift 지원 모듈 경로를 생략함 | 테스트는 실행 Mac의 아키텍처로 검사하고 developer framework·Swift 지원 경로를 사용. 전체 Xcode의 실제 `--tests` 컴파일 회귀 추가 |
| `⌥Space`, 이후 `⌃⌥D`가 다른 기능을 실행하는 듯 보임 | 사용자 보고. 해당 키를 실제로 선점한 앱은 확정하지 못함. 저장된 키 설정만으로 실행 주체를 단정할 수 없음 | 현재 실행 중인 앱과 정확히 겹치는 설정만 진단하고 사용자가 단축키를 선택하도록 안내 |
| 녹음 뒤 글이 안 들어가고 입력 완료 확인 실패 | TextEdit의 접근 권한·입력란·포커스·스냅샷 검사는 모두 통과했지만 붙여넣기 뒤 값이 바뀌지 않음 | 녹음 없는 고정 문장 테스트로 AI 처리와 입력 실패를 분리 |
| 녹음 없는 테스트에서도 `ㅍ` 한 글자만 입력 | 한글 입력 상태에서 V만 전달됨. Karabiner 16.3.0의 CGEvent fallback은 일반 키 이벤트의 Command flag만으로 modifier 상태를 만들지 않음 | 별도의 Command 누름 → V 누름 → V 뗌 → Command 뗌 이벤트를 private event source에서 생성 |
| 앱 교체 뒤 키체인 인증 때문에 창이 뜨지 않음 | 기존 암호화 기록을 여는 Keychain 호출이 앱 초기화의 메인 스레드를 막음. 새 ad-hoc 코드의 접근 인증이 필요 | 창을 먼저 열고 백그라운드에서 준비, 진행·실패·재시도 상태를 표시 |
| 이미 허용한 마이크·손쉬운 사용 권한을 다시 확인해야 함 | ad-hoc 앱 교체가 안정된 Developer ID 신원을 제공하지 않음. 권한 상태 갱신도 별도 필요 | 앱 활성화 시 상태 갱신. Apple가 요구하는 확인은 사용자에게 정확히 안내 |
| Groq 음성 인식을 유지하면서 문장 정리만 OpenRouter로 바꿀 수 없음 | 기존 설정의 provider 하나가 두 단계를 결정 | 음성과 문장의 제공자·모델·키를 분리하고 기록·사용량·실패 녹음 복구에도 동일하게 적용 |
| `오픈 라우터`, `원 패스워드`가 한글로만 출력 | 문장 정리의 기술명 표기 규칙이 충분하지 않음 | 받아쓰기에서 확실히 식별한 이름을 `OpenRouter`, `1Password` 등 공식 표기로 복원. 일반 한국어와 명시한 한글·인용·식별자는 유지 |
| 키가 저장됐다는 표시가 실제 연결 성공처럼 보임 | Keychain 저장 여부와 제공자의 모델 접근·잔액·실제 처리 성공은 별개 | 음성·문장 연결을 나누어 표시하고, 실제 연결 여부는 처리 결과로 확인 |
| 1Password CLI 인증이 시간 초과됨 | 사용자 인증이 필요한 실행에서 비대화형 CLI가 대기. `op vault ls` 성공만으로 이후 모든 키 읽기가 보장되지는 않음 | 키는 채팅·명령 인자·평문 파일로 옮기지 않고, 필요 시 실제 실행 요청을 사용자 터미널에서 인증 |
| 저장소의 SSH fetch 인증 실패 | 1Password SSH agent가 서명을 반환하지 못함. 앱 설치·음성 API 동작과는 별개의 개발 환경 문제 | 공개 배포 앱 설치에는 Git·SSH를 요구하지 않음. 개발 작업은 이미 인증된 GitHub CLI의 HTTPS 경로로 확인하며 전역 SSH 설정은 변경하지 않음 |

일반 사용자와 개발자를 위한 실행 절차는 [새 Mac 설치 안내](../../mac-installation.md), 입력 이벤트와 단축키의 자세한 근거는 [별도 기록](input-and-shortcuts.md)을 참고한다. 입력 실패를 단축키 충돌로 일괄 설명하거나, Karabiner 설정을 끄는 방식으로 처리하지 않는다.

## 검증 결과

- 공개 ZIP의 SHA-256, 코드 서명, Sparkle Ed25519 서명과 공개 업데이트 채널을 확인한 뒤 설치했다. 새 단독 설치 스크립트의 `--verify-only`로 공식 v0.1.10 ZIP을 다시 확인했으며 현재 설치 앱은 교체하지 않았다.
- 초기 설치·빌드 사전 검사 회귀 26개가 통과했다. 합성 다운로드·하드웨어·서명 결과와 실제 macOS의 ZIP·plist·파일 교체·quarantine 처리를 사용해 checksum 거부, 설치 중 앱 실행 거부, 버전 내려감 거부, 실패 복원과 명시한 SDK 보존을 확인했다.
- 실제 Sparkle 시험 도구를 지정한 초기 전체 Python 도구 테스트는 141개 통과, 제외 0개, 실패 0개였다. 이후 XCTest 경로·host 검사 보완의 관련 회귀는 로컬 10개 통과, 전체 Xcode가 없는 CLT에서 실제 Xcode 검사 1개 제외였다. 해당 검사는 Xcode가 선택된 CI에서는 반드시 실행한다.
- 입력 이벤트 회귀 검사는 기존 구현에서 실패하고 새 4개 이벤트에서 통과했다. 이벤트 생성만 검사하며 시험 프로그램은 키를 다른 앱에 보내지 않는다.
- 수정 설치 앱의 실제 입력 로그에서 `confirmed.paste`를 3회 확인했다. 클립보드 복원도 성공했다. 이는 설치 앱의 입력 성공 증거이며, 모든 앱·모든 키보드 구성의 성공 증거는 아니다.
- 실제 앱의 처리 경로를 컴파일한 headless 검사 17개가 통과했다. Groq 음성 → OpenRouter 문장, 키·모델·사용량·기록의 구분, 저장된 설정으로 복구, 음성 키 없는 문장 재처리, 로컬 음성 시작을 포함한다. 과거 제공자의 키 인증을 기다리는 중 설정·개인 사전을 편집해도 시작 당시 제공자·키·사전을 사용하는 복구 경합도 확인했다. HTTP는 합성 응답으로 가로챘으며 사용자 키·마이크·네트워크·Keychain을 사용하지 않았다.
- 실제 프롬프트 소스의 공식 표기 계약 검사는 수정 전 17개 실패, 수정 후 0개 실패였다. 모의 HTTP의 제공자 요청 계약 6개도 통과했다. 20개 형식·말투 조합의 최대 지침 크기는 10,378 UTF-8 bytes로 기존 10,400-byte 제한 이내였다. 이는 토큰 수나 모델 품질의 지표는 아니다.
- 실제 앱 초기화·Keychain 캐시 소스를 사용하는 합성 검사 31개가 통과했다. 인증 대기 중 UI 상태 응답, 녹음 차단, 인증 실패·동일 저장소 재시도·기록 보존, 앱 활성화 후 권한 허용과 철회 반영, 같은 제공자의 키 1회 읽기, 로컬 음성에서 사용하지 않는 클라우드 키 조회 생략을 확인했다. 저장하지 않은 초안 배제, 저장·삭제 실패 후 기존 키 유지, 인증 대기 중 제공자를 바꿨다가 돌아오는 경합, 과거 제공자의 복구 키 준비와 취소도 검사했다. 실제 시스템 인증이나 사용자의 Keychain을 호출한 검사가 아니다.
- Karabiner의 단순하고 정확한 키 조합을 읽기 전용으로 비교하는 합성 검사 16개가 통과했다. 조건·장치·wildcard·좌우 modifier 구분을 포함하는 복잡한 규칙은 충돌로 단정하지 않는다.
- 최종 0.1.11 (12) 소스로 macOS 26.5 SDK를 자동 선택한 최적화 앱 빌드와 `codesign --verify --deep --strict`가 통과했다.
- 이 CLT에는 XCTest가 없어 이 기기의 전체 Swift 테스트를 통과했다고 기록하지 않는다. 전체 테스트는 Xcode가 있는 CI에서 별도로 확인한다.

## 실제 모델 비교의 범위

음성은 Groq의 `whisper-large-v3-turbo`를 유지하고, 문장 정리는 OpenRouter에서 비교했다. 사용자 녹음이나 개인 문장 대신 제품명 표기, 자기 정정, 일반 외래어, 명시한 한글 인용의 합성 사례를 사용했다.

이번 OpenRouter GPT OSS 120B 실행에서는 표기 복원 실패와 깨진 문장·응답이 발생했다. Qwen3 30B Instruct는 첫 표기 사례를 성공시켰다. 나머지 검증은 인증 완료 뒤 진행한다. 이 결과는 특정 시점의 공급자 라우팅·파라미터·작은 사례 집합에 대한 결과로, 모델 전체의 한국어 품질 순위를 뜻하지 않는다. 공개 가격이나 키 저장만으로 품질·연결 성공을 판단하지 않는다.

원본 로컬 검증 산출물은 Git에서 제외한 `build/macbook-verification/`에 보관한다. 키 값, 사용자 문장, 녹음, 개인 vault 식별자는 공개 문서·PR에 포함하지 않는다.

## 여러 Mac에서 남는 필수 단계

지원 범위는 Apple Silicon M1 이후, macOS 14 이상이다. 배포 앱을 설치할 때 Swift·Xcode·로컬 음성 모델은 필요하지 않다. 클라우드 음성 인식을 선택하면 로컬 모델을 내려받지 않는다. API 키와 마이크·손쉬운 사용 권한은 각 Mac에서 준비해야 한다.

0.1.12도 기존 커뮤니티 ad-hoc 서명 방식을 유지한다. Developer ID 서명과 Apple 공증은 이번 작업 범위에서 제외하며, 커뮤니티 배포의 선행 조건으로 두지 않는다. 이 방식에서는 다운로드 경고와 앱 교체 후 권한·Keychain 재인증이 발생할 수 있다. [기존 공증 배포 경로](../../updates.md)는 향후 배포 방식을 변경할 때 참고할 수 있도록 유지한다.

Gatekeeper·TCC를 끄거나, quarantine을 일괄 삭제하거나, 모든 앱에 키체인 접근을 허용하는 방식으로 설치를 단순화하지 않는다. macOS가 요구하는 사용자 인증은 자동화로 대신할 수 없다.

## 공식 근거

- [Apple `SecItemCopyMatching`](https://developer.apple.com/documentation/security/secitemcopymatching(_:_:)): 키체인 조회는 호출 스레드를 막을 수 있으므로 UI 스레드와 분리한다.
- [Apple 코드 서명과 Keychain 신원 추적](https://developer.apple.com/library/archive/technotes/tn2206/_index.html): Keychain은 코드의 designated requirement를 이용해 접근 신원을 추적한다. 공증과 권한 허용은 서로 다른 판단이다.
- [Apple 공증 배포](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution): Developer ID 서명과 notarization 배포 절차.
- [OpenRouter GPT OSS 120B](https://openrouter.ai/openai/gpt-oss-120b), [Qwen3 30B Instruct](https://openrouter.ai/qwen/qwen3-30b-a3b-instruct-2507): 공개 가격과 공급자 목록. 실제 계정 접근·표기 품질은 별도로 확인한다.
