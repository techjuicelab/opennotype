# Jev 활용 흐름 확장 — 0.1.18(20)

추천했던 우선순위 8개를 사용자가 비교·확인하는 흐름에 연결했다. 이전의 의미 검토와 자동 입력 보호는 유지한다. 새 기능은 사용자가 버튼을 눌러 전송을 확인할 때만 API를 호출한다. 사용자의 텍스트·사전·설정을 무인으로 변경하거나 더 비싼 모델로 자동 전환하지 않는다.

| 우선순위 | 적용 내용 | 진입 위치 | 추가 호출 |
| --- | --- | --- | --- |
| 1 | 표기 후보의 판단 보류·추가 확인·후보 권고와 상세 점수 | Jev 검토 결과 | 없음 |
| 1 | `오픈 라우터에 → OpenRouter에` 같은 구문 교정의 Jev 검토, 확인 저장, 마지막 저장 되돌리기 | 개인 사전 → 확인할 교정 | 검토 1회 |
| 1 | 기존 결과와 개선안을 나란히 비교하고 원하는 결과 복사 | 최근 결과/기록의 Jev 검토 → 개선안 만들기 | 생성 최대 1회 + 검토 최대 1회 |
| 2 | 원문과 결과의 변경 토큰·숫자 표시, 의미/추가/누락 신호와 구분 | Jev 검토 → 원문 비교 | 없음 |
| 2 | 문장 모델별 생성 시간·검토 건수·경고 비율·검토 지연·개선안 생성/복사 집계와 비용 비교 | 사용량 → 이번 실행의 Jev 검토 비교 | 없음 |
| 2 | 번역과 선택 수정의 목적에 맞는 수동 검토 | 최근 결과, 완결된 번역 재처리 미리보기 | 검토 1회 |
| 3 | 개선안용 보조 모델을 같은 제공자의 모델 목록에서 선택 | 설정 → AI 연결 → Jev → 보조 모델 | 개선안 요청 때만 |
| 3 | 큰 사전에서 직접 관련 항목을 우선하고 무관한 최근 항목 최대 32개로 제한 | 201개 이상 사전의 문장 처리 | 없음, 로컬 선별 |

큰 사전의 의미 선별을 위해 별도 Jev 선행 요청을 추가하면 저렴한 문장 모델보다 비싸고 느릴 수 있다. 이번에는 이미 보유한 원문과 사전의 로컬 관련성으로 줄였다. 추가 비용을 발생시키는 의미 라우팅·매 문장 자동 재생성·개인정보 자동 판별은 적용하지 않았다.

## 전송과 보관

- 받아쓰기 자동 검토 설정은 기존대로다. 번역·선택 수정은 자동 검토 대상에 추가하지 않았다.
- 최근 번역에는 그 작업의 목표 언어, 선택 수정에는 당시 선택 원문·음성 수정 지시를 snapshot으로 묶어 검토한다. 현재 선택 영역을 다시 읽거나 바뀐 설정으로 과거 언어를 추정하지 않는다.
- 과거 번역·선택 수정 기록에는 필요한 원문/목표 언어가 없어 직접 검토를 제공하지 않는다. 번역 기록을 명시적으로 다시 처리한 경우 그 미리보기는 당시 사용한 언어로 검토할 수 있다.
- 개선안 생성에는 원문·이전 결과·선별 사전·당시 목적과 프로필을 보내며 주변 문맥·오디오는 제외한다. 개선안은 자동 재시도 없이 생성 요청 최대 1회로 제한한다. 기존 생성 API의 단일 JSON 결과 파서를 사용하고 이전 결과는 지시문이 아닌 데이터로 보낸다.
- 개선안 검토 실패 시 ‘미검토’임을 표시한다. 낮은 위험 점수도 정확성이나 개선을 보장하지 않는다. 다른 앱에 재입력하거나 문장 기록을 덮어쓰지 않는다.
- 교정 제안은 한 번의 연속된 한영 표기 변경만 추출한다. 기존 자동학습의 범위를 넓히지 않는다. Jev의 `use_candidate`와 낮은 위험 신호가 있어도 별도 저장 확인이 필요하다.
- 저장은 교정 후보 전체 값·만료·기존 사전 값을 한 트랜잭션에서 비교한다. 다른 인스턴스가 삭제/변경한 후보는 저장하지 않고 성공한 후보 ID만 지운다. undo는 이후 수동 편집을 덮어쓰지 않는다.
- 검토·개선안은 메모리에만 둔다. 새 작업·기록 삭제·검토 연결/키 변경·취소로 무효화하며 늦은 응답을 폐기한다.
- 품질 비교는 이번 앱 실행의 집계이며 원문을 담지 않는다. 검토 경고율은 오류율이 아니고, 개선안 복사는 실제 수정 성공률이 아니다. 비용은 사용량 화면의 선택 기간 전체 문장 처리 비용이므로 검토 표본만의 비용과 다르다. 사용량 기록을 끄거나 초기화하면 메모리 집계도 초기화한다.

## 검증 범위

Core 요청/응답 계약, 불확실성 표시, 구문 추출·CAS 저장, 큰 사전 선별, 개선안 프롬프트, 모드 snapshot, 취소·삭제 후 늦은 응답, 실제 제공자 연결을 검사한다. 정식 XCTest는 Xcode가 있는 GitHub CI에서 실행한다. 합성 사례와 실제 사용자의 정확도는 구분한다.

### 실행 결과

- 실제 Core/화면 helper 격리 검사 32건, 품질 집계/사용량 25건, 사전·저장소 관련 70건 통과. 이는 실제 테스트 본문을 사용한 headless 검사이며 정식 XCTest와 구분한다.
- 로컬 Python 171건 중 168건 통과·환경 제외 3건. release 앱 빌드와 코드 서명 검증 통과.
- 실제 TypeSafe·OpenRouter 각각 받아쓰기·번역·선택 수정 정상/오류 쌍 6건, 총 12건 모두 유효 응답. 두 연결에서 이번 정상 3건은 보호 기준 미만, 오류 3건은 0.9 이상이었다. 최대 응답 시간은 각각 0.679초와 1.063초였다. [신호 원자료](jev-workflows-signals.json)
- 개선안 2건은 실제 Qwen 요청과 응답 파서로 생성했다. 이전 결과의 ‘네 시’를 원문의 ‘세 시’로 복원했고, ‘제브 J E V’는 `JEV` 하나로 정리했다. 생성 2.276초/1.565초, 후속 TypeSafe 검토 0.620초/0.604초였다. 생성 보고 비용 합계 $0.00029686275, 검토 추정 합계 $0.000081480이다. [개선안 평가](jev-workflows-improvements.json)
- 설치 앱 UI에서 기존 `JEV로 정상 입력이 됩니다.` 시험 기록을 명시적으로 검토한 뒤 개선안 생성→Jev 검토→원문/개선안 비교를 확인했다. 기존 문장이 이미 적절해 같은 문장을 반환했다. 기록 수는 12개를 유지하고 자동 입력은 하지 않았다. 사용량 화면에는 해당 모델의 검토 1건·개선안 생성 1건이 나타났다. 과거 기록은 생성 모델 ID가 없으므로 첫 수동 검토를 현재 모델에 억지로 귀속하지 않았다.
- 최초 GitHub XCTest는 `reviewLearningCandidate`에서 Observation property의 읽기/수정이 겹치는 런타임 충돌을 발견했다. 값을 지역 변수로 먼저 평가하도록 고쳤다. 이어서 녹음 중 문장 제공자를 바꿔도 녹음 시작 때의 검토 설정을 지켜야 하는 기존 회귀 검사 실패를 수정하고, 새 보조 모델 설정의 이전 버전 migration 검사를 보완했다. 격리 Core 검사만으로 앱 런타임 검증을 대체할 수 없다는 사례다. 최종 정식 XCTest·Python·앱 빌드 결과는 [PR #9의 Checks](https://github.com/techjuicelab/opennotype/pull/9/checks)에 연결한다.

합성 텍스트와 제한된 앱 UI 검사이며 새로운 버전의 마이크·다른 앱 자동 입력을 다시 입증한 것은 아니다. 이 경로는 앞선 0.1.17에서 사용자가 직접 JEV 입력 성공을 확인했다. Jev의 낮은 위험 신호나 동일한 개선안은 전반적인 정확도 보장이 아니다.
