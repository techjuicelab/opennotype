# 받아쓰기 표현과 AI 편집 강도

0.1.22에서 **설정 → 입력·단축키 → 받아쓰기 표현**에 표현 방식과 강도 게이지를 추가했다. 새 설치와 기존 설정의 기본값은 **현재 받아쓰기 · 강도 0**이다. 기본값에서는 지금까지 사용한 말실수·반복 정리, 한영 혼합 표기와 사실 보존 정책을 그대로 사용한다. 음성 인식 모델이나 문장 정리 모델을 바꾸는 설정이 아니다.

0.1.23은 기본값의 문장·절 재시작과 추임새 정리를 보완했다. 표현 방향·강도 설정은 그대로이며, [실제 전후 시험과 한계](reviews/2026-10-02/faithful-restarts.md)에 결과를 기록했다.

## 방향과 강도

| 표현 방식 | AI에 요청하는 변화 |
| --- | --- |
| 현재 받아쓰기 | 기존처럼 말실수와 우발적인 반복을 정리하고 말한 내용을 보존한다. |
| 간결하게 | 같은 뜻과 중요한 정보를 더 짧고 단순하게 표현한다. |
| 핵심 요약 | 필요한 요청과 핵심을 앞세우고 중요하지 않은 말의 틀과 곁가지를 줄인다. |
| 명확하게 | 두서없는 생각의 순서와 이미 말한 관계를 정리해 목적을 분명히 한다. |
| 자세하게 | 말한 내용 안에서 설명과 연결을 더 풀어 쓴다. 새로운 지식을 덧붙이지 않는다. |
| 창의적으로 | 사실과 의도를 유지하면서 어휘, 문장 구성과 리듬을 바꾼다. |

강도는 **0~100**이며 화면에서는 5씩 조절한다. 1~33은 가볍게, 34~66은 적당히, 67~100은 적극적으로 요청한다. 강도는 정확도 백분율이나 보장된 길이 감소율이 아니다. 문장의 내용과 선택한 모델에 따라 결과가 달라지며, 길이가 항상 일정한 비율로 줄거나 늘어난다는 뜻도 아니다.

**요약과 자세하게는 서로 다른 방향**이다. 요약의 강도를 높이면 핵심 위주로 더 줄이고, 자세하게의 강도를 높이면 원문에 근거한 설명을 더 풀어 쓴다. 방향을 먼저 선택한 뒤 강도를 조절한다. 강도가 0인 상태에서 현재 방식 외의 방향을 새로 고르면 강도 40에서 시작한다. 이미 강도를 올렸다면 방향을 바꿔도 그 강도를 유지한다. 강도를 0으로 내리면 방향 선택은 남아 있어도 기존 받아쓰기 방식으로 처리한다. **현재 방식으로 되돌리기**는 방향과 강도를 함께 기본값으로 복원한다.

## 적용 범위와 보호 조건

- 변경한 설정은 **다음 녹음부터** 적용한다. 녹음 시작 때 선택한 설정을 기억하므로 녹음 도중 게이지를 바꿔도 진행 중인 결과는 바뀌지 않는다.
- 모든 앱의 **받아쓰기**에 적용한다. 기존 앱별 작성 형식과 말투 설정은 계속 유지한다. 번역과 선택 문장 수정에는 적용하지 않는다.
- 강도가 0이거나 현재 받아쓰기이면 기존 생성 지시문과 입력 payload를 그대로 유지한다. STT의 음성 인식 힌트에도 표현 방향을 보내지 않는다.
- 숫자·날짜·이름·식별자·인용·조건·부정·불확실성과 부탁이나 약속의 강도를 지킨다. 요약에서도 중요한 제한이나 필요한 행동을 없애면 안 된다.
- 자세하게와 창의적으로도 새로운 사실, 이유, 사례, 진단, 답변이나 더 강한 약속을 만들어서는 안 된다. 원문에서 확정하지 않은 선택지를 AI가 대신 결정하지 않는다.

표현 설정은 기존 문장 정리 요청에 함께 전달하며 자체적으로 추가 API 요청을 만들지 않는다. 지시문과 출력 길이가 달라질 수 있으므로 실제 토큰 비용까지 동일하다는 뜻은 아니다. Jev는 사용자가 선택한 기존 검토 모드와 연결을 따른다.

## Jev와 기록

Jev 검토에는 생성에 사용한 **동일한 표현 방향과 강도**를 전달한다. 선택한 요약·반복 정리·재서술은 오류로 취급하지 않고, 그 방향으로도 허용하지 않은 사실·의도 변경을 검토한다. 입력 전 교정을 사용하면 교정안 생성과 재검토에도 같은 설정을 유지한다. 실패·시간 초과·취소 시의 기존 보류 및 취소 정책도 유지한다.

새 받아쓰기 기록에는 당시 프로필을 함께 보관하여, 나중에 검토할 때 현재 게이지 대신 그 결과를 만들 때의 설정을 사용한다. 이전 기록에 새 설정이 없으면 기존 받아쓰기 정책으로 검토한다. 기록의 **다시 처리**는 현재 설정으로 새로운 미리보기를 만드는 별도 동작이며, 이미 입력한 글을 자동으로 바꾸지 않는다.

## 합성 평가 명세

[16개 합성 품질 사례](fixtures/dictation-expression-quality.json)는 기본값·비활성화 대조군, 각 표현 방향의 가벼운/강한 편집, 영어와 한영 혼합, 조건·부정·수치·식별자·불확실성을 다룬다. `expected_text`는 사람이 작성한 가능한 결과 예시이며 실제 모델의 통과 결과가 아니다. 같은 의미의 다른 표현도 허용한다. regex는 일부 보존 조건을 검사할 뿐이며, 방향에 맞는 편집과 전체 의미는 함께 검토해야 한다.

기존 fixture와 새 fixture는 같은 실제 Core 요청 생성·파서를 사용한다. 표현 설정이 없는 기존 fixture는 이전과 같고, 설정이 있는 fixture는 `writing_profile.expression`에 `style`과 `strength`를 명시한다. 알 수 없는 스타일이나 잘못된 강도는 평가를 중단하여, 의도한 요약 시험이 조용히 기본 받아쓰기로 바뀌지 않게 한다.

다음 명령은 키 접근과 네트워크 요청 없이 실제 Core 요청을 생성하고 비용 예약만 계산한다.

```sh
python3 scripts/compare-text-models.py \
  --fixtures docs/fixtures/dictation-expression-quality.json \
  --models openai/gpt-6-luna \
  --output build/dictation-expression/dry-run.json
```

실제 모델 호출이나 자연 발화 시험은 별도 검증이다. 기본 프롬프트의 바이트 보존, 저장 호환성, 요청 전달 검사만으로 각 표현 방식의 실제 품질이 입증되지는 않는다.

### 실제 시험에서 보완한 의도 보호 기준

첫 GPT-6 Luna 합성 시험에서 기존 regex는 16개 모두를 통과시켰지만, 수동 검토로 아래 세 가지 의도 변화를 발견했다. 이름·시각·부정이 남았다고 해서 문장의 의도까지 보존됐다고 판단할 수 없었다.

| 사례 | 원래 의도 | 발견한 문제 |
| --- | --- | --- |
| EX10 · 강한 핵심 요약 | OpenNoType을 **개선하고 싶다**는 희망 | “개선하고, … 보내 주세요”로 합쳐 개선하라는 명령으로 강화했다. |
| EX14 · 영어 요약 | **I want JEV to improve OpenNoType.** | **Improve OpenNoType with JEV.**로 바뀌어 개인적 희망이 명령이 됐다. |
| EX13 · 창의적 표현 | 다듬고 싶다는 희망과 **읽기 쉽게 표현을 바꿔 달라**는 별도 요청 | 다듬고 싶다는 문장과 뜻 유지 요청만 남아 실제 표현 변경 요청이 약해졌다. |

평가 명세에 원문에 있는 희망과 행동 요청을 따로 검사하는 기준을 추가했다. “싶어요”나 “I want”라는 한 가지 문자열만 강제하지 않는다. “개선하기를 바랍니다”, “받기를 원해요”, “I would like”처럼 동등한 표현을 허용한다. 조건절 안에서 행동을 언급했다는 이유만으로 직접 요청이 보존됐다고 판단하지도 않는다.

명료화 예시 EX04·EX11의 원문에도 “결과를 받고 싶어요”가 있으므로, 작성한 기대 예시 역시 새 전달 명령으로 바꾸지 않고 그 희망을 유지하도록 바로잡았다. 입력 발화는 변경하지 않았다. 새 regex는 이 세 가지 관찰된 실패를 회귀 검사하지만 모든 발화 의도를 판정하는 모델은 아니다. 보완된 프롬프트의 실제 개선 여부는 같은 입력을 사용한 재시험과 수동 검토 결과로 따로 확인한다.
