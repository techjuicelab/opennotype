# OpenNoType UI/UX 재정비 시안

기능 개발과 충돌하지 않도록 만든 **독립적인 화면 시안과 적용 설계**입니다. 이후 사용자 승인으로 옵션별 `?` 도움말과 설정 정리, 홈 결과 우선 배치를 실제 SwiftUI 소스에 적용했습니다. 구현 범위와 검증 결과는 [실제 구현 보고](../../../docs/reviews/2026-10-15/uiux-option-help.md)를 기준으로 확인하세요. 아래 HTML은 계속 독립적인 설계 시안입니다.

사용자 요구:

- 늘어난 기능을 더 직관적이고 깔끔하게 재배치.
- 다른 AI 에이전트의 기능 개발과 병행.
- 각 옵션의 긴 설명은 이름 옆 `?` 버튼을 눌러 별도로 확인.
- 설계뿐 아니라 실제 개선 작업도 메인 포함 최소 4개 에이전트를 병렬 운영.

## 우선 적용할 개선

### 1. 긴 설명을 옵션별 도움말로 이동

기본 행은 **옵션 이름 + `?` + 현재값**으로 구성합니다. 필요할 때만 짧은 적용 상태를 한 줄 추가합니다.

| 기본 화면에 남길 것 | `?` 팝오버로 옮길 것 |
| --- | --- |
| 옵션 이름과 현재값 | 기능의 자세한 설명 |
| 현재 미적용 이유 | 어느 작업·언어·모드에 적용되는지 |
| 키·모델·권한 준비 필요 | 준비 방법과 배경 설명 |
| 현재 입력 보류·실패 원인 | 일반적인 실패 계약과 예외 |
| 켜진 실험 기능의 추가 요청·보류 요약 | 전송 대상·추가 비용·상세 주의 |
| 녹음·처리 상태와 종료·취소 | 비교 예시·선택 기준 |

도움말은 단순 hover tooltip이 아니라 클릭으로 여는 팝오버입니다. 한 번에 하나만 열고, 닫기·같은 `?` 다시 누르기·`Escape`·바깥 클릭을 지원합니다. 닫기·Escape·화면 크기 변경으로 도움말이 닫히면 원래 버튼에 포커스를 복원합니다. 바깥의 다른 컨트롤을 클릭한 경우에는 그 컨트롤의 포커스를 존중합니다.

`?`의 접근성 이름에는 옵션 이름을 포함합니다. 값 조작이 비활성화되어 있어도 도움말은 읽을 수 있어야 합니다. 유료 전송·삭제의 기존 확인창은 도움말로 대체하지 않습니다.

### 2. 홈은 단축키와 결과에 집중

- 준비 상태에서는 **입력할 앱에서 사용할 단축키**가 중심입니다.
- 일반 받아쓰기를 홈 창에서 시작하는 새 버튼을 만들지 않습니다. 기존 외부 앱의 입력 대상 보호를 유지합니다.
- 최근 결과·원문 비교·복사는 가까이 둡니다.
- 입력 보류·확인 불가가 발생하면 결과와 다음 행동을 맨 위에 표시합니다.
- 번역·선택 문장 수정·프롬프트는 보조 작업입니다. 프롬프트의 기존 복사용 녹음과 외부 입력용 단축키 의미는 유지합니다.
- 녹음 중 경고가 나와도 현재 상태·시간·종료·취소를 가리지 않습니다.

### 3. 기능은 유지하고 탐색을 줄이기

시안의 주 메뉴는 **받아쓰기 / 기록 / 개인 사전 / 설정**입니다. 녹음 복구는 기록 안에서 별도 탭으로 보여 주되, 텍스트 기록과 실패 원음의 저장·만료 정책은 합치지 않습니다.

설정은 **받아쓰기 / 녹음·단축키 / AI 연결 / 개인정보 / 앱 관리 / 고급 도구**로 구분했습니다. 고급 도구 안에서도 실험 기능과 문제 해결을 분리합니다. 현재 켜진 고급 기능은 접혀 있어도 적용 상태를 요약합니다.

이 전체 탐색 개편은 **2차 적용안**입니다. 1차 `?` 도움말 개선 때문에 `AppPage`, `SettingsSection`, 설정 저장 식별자까지 동시에 바꿀 필요는 없습니다.

## 실제 기능과 동일하게 유지할 계약

- 바로 입력은 인식 원문을 입력하는 경로이며 원음의 정확한 복제·정확도 보장은 아닙니다.
- 바로 입력을 저장해 두었어도 번역 출력이면 AI 처리가 적용됩니다. UI가 모순을 숨기려고 저장값을 자동 변경하면 안 됩니다.
- 표현 방식과 강도는 번역·선택 수정에 적용되지 않는 기존 범위를 유지합니다. 강도 0은 AI 정리 전체를 끈다는 뜻이 아닙니다.
- 일반 받아쓰기의 Jev `protect`는 검토 실패 시 기존 결과를 입력할 수 있습니다. `repair`는 실패·미해결 시 보류합니다.
- 번역 보호는 `protect`와 번역 검토를 함께 켰을 때 적용하며 실패 시 보류합니다. 위 일반 받아쓰기 실패 계약과 합치지 않습니다.
- 번역 다듬기 실패 때 초안을 대신 자동 입력하지 않고 보류하는 기존 계약을 유지합니다.
- 개인 사전의 안전한 표기 교정 자동 학습과 확인이 필요한 후보 검토는 구분합니다.
- API 키 저장과 실제 연결 확인, 모델 파일 저장과 메모리 준비, 입력 확인과 입력 여부 불명은 각각 구분합니다.
- 주변 문맥 허용·음성 전송·추가 검토 요청·모델 삭제 등 권한과 데이터 영향을 기존대로 유지합니다.

전체 매핑과 기본값 보존은 [feature-map.md](feature-map.md), 상태·작업 흐름은 [flows.md](flows.md), 문구·도움말·접근성은 [visual-guidelines.md](visual-guidelines.md)에 정리했습니다.

## 기능 개발과 병행하는 적용 방법

### 1차: 설명을 접는 작은 View 변경

먼저 옵션별 `?` 도움말과 설정 행의 위계만 적용합니다. 현재 기능 담당자가 작업 중인 `AppModel`, `Preferences`, 오디오·추론·붙여넣기 코드는 수정 범위에서 제외합니다.

공통 도움말은 SwiftUI `Button` + `popover`로 구현하고 화면 문구는 기존 `L(한국어, 영어)` 경로를 유지합니다. 각 View의 기존 binding·action·표시 조건은 그대로 연결합니다. `.disabled`를 행 전체에 걸어 도움말까지 비활성화하지 않도록 컨트롤 단위로 구분합니다.

실제 코드 작업도 다음처럼 **메인 포함 4개 에이전트를 병렬 실행**했습니다. 아래 파일 소유권으로 구현했고, 추가로 메인은 업데이트 옵션과 홈 결과 순서를 정리하고 에이전트 B는 Jev 보조 설정을 정리했습니다.

| 담당 | 소유할 파일·범위 | 수정하지 않을 것 |
| --- | --- | --- |
| 메인 | 신규 공통 `OptionHelp` 컴포넌트, 공통 행 규칙, 최종 통합·빌드·교차 검토 | 기능 담당자의 엔진·저장·입력 정책 |
| 에이전트 A | `DictationTranslationSettingsView.swift`, `DictationExpressionSettingsView.swift`, `TranslationRefinementSettingsView.swift` | 표현·번역 알고리즘, 기본값 |
| 에이전트 B | `VoiceInputOptionsView.swift`의 녹음·로컬 모델 옵션 | `AudioRecorder`, `LocalTranscriber`, 장치·모델 수명주기 |
| 에이전트 C | `SettingsView.swift`의 연결·문체·개인정보·일반 설명 재배치 | `Preferences` 저장 형식, Keychain 로직 |

작업 시작 전 각 파일의 최근 변경과 다른 작업자의 소유 범위를 다시 확인합니다. 같은 UI 파일을 기능 담당자가 수정 중이면 별도 checkout에서 UI 변경만 준비하고, 기능 변경이 안정된 뒤 현재 소스와 비교해 통합합니다. 작업 중인 디렉터리를 예전 사본으로 덮어쓰지 않습니다. 공동 파일은 메인만 수정합니다.

### 2차: 홈·탐색·기록 화면 재구성

1차가 통합되고 기능 추가가 안정되면 홈 결과 우선 배치, 설정 목적지 재편, 기록 목록·상세 구성을 적용합니다. 이때도 실제 변경 파일을 서로 겹치지 않게 나눠 최소 4개 에이전트를 병렬 운영합니다.

`AppPage`나 `SettingsSection` 변경이 필요하면 기능 담당자와 공유하는 계약 변경으로 별도 취급합니다. 기존 딥링크·상태 복구·키보드 탐색·메뉴바 진입과 레이아웃 테스트를 확인한 후 적용합니다.

### 3차: 네이티브 화면과 실제 입력 검증

View 컴파일과 시안 검사는 실제 macOS 동작의 증거가 아닙니다. 네이티브 팝오버의 접근성 이름·VoiceOver·키보드 탐색, 작은 창·다크 모드, 입력 보류 결과 노출, HUD가 외부 앱 포커스를 빼앗지 않는지 별도로 확인해야 합니다.

설치·실행·실제 마이크·외부 입력 검증은 진행 중인 기능 작업과 충돌하지 않는 순서로 수행합니다. 녹음·설정·기록·권한이 보존되는지 확인하며, 기존 프로그램을 시안 때문에 교체하지 않습니다.

## 실제 조사·시안 팀

메인 포함 4개 에이전트를 실제로 병렬 실행했습니다. 분석 이후 각자 문서 하나를 소유했고, 메인의 클릭 시안을 다시 독립 검토했습니다.

| 담당 | 기여 |
| --- | --- |
| 메인 | 화면 구조 통합, 클릭 시안, 팝오버 동작, 브라우저 검증, 적용 단계 |
| `ux_primary_flow` | 첫 사용·받아쓰기·보류·기록·복구 흐름, 포커스·작업 계약 검토 |
| `ux_settings_architecture` | 기존 기능 전체 이동표, 기본값·Jev·전송·저장 계약 검토 |
| `ux_visual_copy` | 시각 위계·명칭·옵션 도움말·접근성, 색상·포커스 검토 |

## 검증 범위와 제한

- 현재 UI 문제는 SwiftUI 호출 구조와 사용자가 제공한 설정 스크린샷을 기준으로 확인했습니다. 설치 앱 전체 화면을 새로 실행해 감사한 결과는 아닙니다.
- 브라우저에서는 자체 HTML 시안만 열었습니다. 사용자 앱·마이크·API·설정은 조작하지 않았습니다.
- 옵션 도움말 표시, 한 개씩 열기, 닫기·Escape·포커스 복원, 화면 경계, 라이트·다크, 저장값과 유효 상태의 구분을 확인합니다. 실제 수행 결과는 [verification.md](verification.md)에 기록합니다.
- 음성·문장 모델 비교, API 키·권한·삭제 등은 진입 화면만 표현한 시안입니다. 실제 서비스 실행 기능은 구현하지 않았습니다.
- 실험·추가 비용·보류 조건을 짧게 표시하고 자세한 설명을 도움말에 넣는 제안이지, 기존 정책이나 기능을 없애는 제안이 아닙니다.
- 기능 작업이 계속 진행되므로 문서의 소스 행 번호·준비 상태는 구현 직전 재확인해야 합니다.
